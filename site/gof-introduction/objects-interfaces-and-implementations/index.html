Objects, Interfaces and Implementations

Core ideas

What this lesson establishes

Three terms carry the lesson, each defined in the section in its own words; they are the vocabulary of every pattern that follows.

1

Interface and type

An operation's signature is its name, its parameters and its result; an object's interface is the set of all its signatures, the requests it accepts. A type is a name for an interface. One object can have several types, very different objects can share one, and a subtype's interface contains its supertype's.

2

Dynamic binding and polymorphism

Dynamic binding is the choice, made when the program runs, of which object's operation answers a request. It lets one object stand in for another with the same interface, which is polymorphism: the client assumes only that the object supports the interface.

3

Class versus interface inheritance

An object's class says how it is implemented; its type says only which requests it answers. Class inheritance shares code and representation; interface inheritance, or subtyping, says when one object can stand in place of another. Many languages run the two together.

The material

The section's argument first, then the principle, then the count

Read the first part of Section 1.6, up to and including Programming to an Interface, not an Implementation, in your own copy first. The lesson reads it as an argument that ends in a principle, and then counts dependencies.

“Program to an interface, not an implementation.” The authors set that on a line of its own in Section 1.6, How Design Patterns Solve Design Problems, and explain it at once: “Don't declare variables to be instances of particular concrete classes. Instead, commit only to an interface defined by an abstract class.” This lesson reads the section from its start to that principle. Read it in your own copy first.

Section 1.6 is a list of everyday design problems and the ways patterns help with each. The first is finding the objects. An object packages data with the operations on it, and a client can only send it requests; that restriction is what keeps its state encapsulated. Deciding what the objects should be is the hard part, the authors say, because encapsulation, granularity, dependency, flexibility, performance and reuse all pull in different directions, and methods disagree: underline the nouns, follow responsibilities, or model the real world. Many classes do come from analysis, but a design that only copies today's world is not ready for tomorrow's, and some of the most useful objects have no counterpart in it: an algorithm made an object (Strategy), each state of something made an object (State), found late, as a design is made flexible.

The second is granularity: objects can be as small as a character or as large as a subsystem. Patterns help here as well. Facade makes a whole subsystem one object, and Flyweight supports very many tiny ones; Abstract Factory and Builder produce objects whose only job is to make other objects, and Visitor and Command objects whose only job is to carry out a request on something else.

Then interfaces. Each operation has a signature, and the set of an object's signatures is its interface, every request it will accept. A type is a name for an interface, so an object that accepts every request named in a type has that type, and a subtype's interface includes its supertype's. Objects are known only through their interfaces, which say nothing about how the requests are carried out. Which operation runs depends on the request and on the object that receives it, decided when the program runs: that is dynamic binding, and the freedom it gives to swap one object for another of the same type is polymorphism. Patterns often say what belongs in an interface (Memento's two, one narrow and one privileged) and how interfaces must relate (a Decorator's and a Proxy's match the object they wrap).

Then implementations. A class defines an object's data and operations; a subclass inherits both and may override; an abstract class exists mainly to define an interface for its subclasses and cannot be instantiated. The section's key distinction follows. An object's class is how it is built; its type is only what it can be asked. Class inheritance reuses code and representation; interface inheritance says what may stand in for what. C++ and Eiffel use one mechanism for both, and Smalltalk's inheritance is of implementation only, since its variables have no declared types. Java, which came later, gives interface inheritance a keyword of its own, interface, which is why the sketches here use it where the book has a pure abstract class.

That distinction is what the principle rests on. Inheritance is a quick way to define a new kind of object from an old one, but its other use matters as much: when every subclass of an abstract class keeps its interface, all of them are subtypes, and clients can use any of them. Clients that deal with objects only through such an interface need not know the objects' types or the classes that implement them, and the implementation dependencies between parts of a system shrink accordingly. Concrete classes still have to be instantiated somewhere, the authors add; the creational patterns are ways of doing it without the rest of the code naming them.

// The locker names every sender it might use.
final class LockerApp {
    private final SmsSender sms = new SmsSender();
    private final EmailSender email = new EmailSender();
    private final PushSender push = new PushSender();

    void parcelArrived(Customer c, String box) {
        String text = "Your parcel is in box " + box;
        if (c.prefers() == Channel.SMS) {
            sms.text(c.phone(), text);
        } else if (c.prefers() == Channel.EMAIL) {
            email.mail(c.address(), "Parcel", text);
        } else {
            push.send(c.deviceId(), text);
        }
    }
}

That is a parcel locker's app, written to three implementations: it names a text sender, a mail sender and a push sender, and chooses among them itself. The preset concrete-senders writes its dependencies as records, user then used. The lab counts 4 classes, 3 distinct uses and 6 possible pairs, of which 3 are connected, printed reduced as 1/2 = 50%. The largest fan-out, the most classes one class uses, is LockerApp 3. The largest fan-in, the most users one class has, is a tie at 1 among the three senders, broken alphabetically to EmailSender, and the banner names the others.

// The locker commits only to a type: anything that can send a notice.
interface Notifier {
    void send(Customer c, String text);
}

final class LockerApp {
    private final Notifier notifier;

    LockerApp(Notifier notifier) {   // the caller chooses the class
        this.notifier = notifier;
    }

    void parcelArrived(Customer c, String box) {
        notifier.send(c, "Your parcel is in box " + box);
    }
}

Written to an interface, the app depends on one type, Notifier, and each sender implements it. The preset one-interface has 5 classes and 4 uses, connecting 4 of its 10 pairs (2/5 = 40%), and the figures turn round: the largest fan-in is Notifier 4, and no class uses more than one other, so the largest fan-out is a tie at 1. The two presets with a postal sender added show what a new variant reaches. With concrete senders, LockerApp gains a use and its fan-out becomes 4: the client is edited. Through the interface, the new use runs from PostSender to Notifier, and the app is untouched. The lab leaves out the line that creates a PostSender and hands it to the app; that line is what the Creational Patterns course is about.

Finding where a client commits to a class

Four steps, the last of them on code of your own.

1

List what the client uses

Write one record for each class or interface the client names in a field, parameter, local variable or constructor call.

2

Mark the concrete ones

Mark each used name that is a concrete class rather than an interface or abstract class. Those are the client's commitments to an implementation.

3

Add a variant on paper

Add one more implementation of the thing that varies, and write down which existing classes gain a record. If the client is one of them, it must be edited for every new variant.

4

Do it on code of your own

Pick a class in your own code that chooses among several implementations with an if or a switch. Count its fan-out, then count it again with the choices behind one interface, and say where the concrete classes would be created instead.

Common mistakes

1
Taking an object's class and its type for the same thingSection 1.6 separates them: the class says how an object is implemented, the type only which requests it answers. A single object may carry several types, and unrelated classes may share a type; on the lesson's illustration, three unrelated sender classes all have the type Notifier.
2
Expecting the real world to supply every objectThe authors grant that many classes come from analysis, but warn that a design which only models today's world may not suit tomorrow's. Some of the objects that make a design flexible, an algorithm or a state made into an object, have no counterpart in the world and appear only as the design is worked.
3
Thinking an interface removes concrete classes from the programConcrete classes must be instantiated somewhere, as the section says itself. Programming to an interface moves the naming of them out of the clients; the creational patterns say where it goes.
