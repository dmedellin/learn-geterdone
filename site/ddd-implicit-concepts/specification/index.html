Specification

A test method on an object is often a little rule, and some rules grow until they swamp the object they test. Read Evans's case for keeping such rules in the domain layer as predicate-like value objects, the pattern he developed with Martin Fowler, then check seed lots against a seed bank's distribution rule, clause by clause.

Specification in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson. The first is logic programming's, the second the pattern's, the third the lab's.

1

Predicate

A function that returns true or false and can be combined with others by and and or to state a more complicated rule. Evans borrows the idea from logic programming without adopting the whole paradigm.

2

Specification

A value object whose one job is to say whether another object meets some criteria. It keeps a business rule in the domain layer without loading it onto the object being tested.

3

A clause

In the lab, one comparison in a specification, such as moisture at most 8. The lab evaluates each clause on the candidate and reports which are true and which is the first, in the order written, that is false.

The material

The problem first, then the pattern, then a lot checked

Read Specification in Chapter 9, up to Applying and Implementing Specification, in your own copy first. The lesson reads the pattern as a tool, then checks single candidates against one.

“In all kinds of applications, Boolean test methods appear that are really parts of little rules.” That is how Evans opens Specification, the narrowest of the three kinds of concept Chapter 9 names and, he says, a common one. He developed the pattern with Martin Fowler. Read the pattern in your own copy first, up to Applying and Implementing Specification, which is the next lesson.

The problem is a test method that grows. A method that asks whether a bill is past its due date is a one-line rule, and it belongs on the bill. A method that asks whether the bill is delinquent starts the same way, then needs a grace period that depends on the customer's account, the payment history, policy for different product lines, and the difference between a bill due a second notice and one due for a collection agency. The object's plain meaning, a request for payment, disappears under the rules, and it picks up dependencies on classes and subsystems that have nothing to do with that meaning.

The usual rescue, Evans says, is worse. Developers move the rules out to the application layer, which leaves the domain object a bundle of data that no longer expresses the rules of the business, while the rules sit in code that is not about the model. The rules belong in the domain layer, and they do not fit in the object being tested.

Logic programming has an answer: rules written as predicates, functions that return true or false and combine with and and or. Evans notes that people have tried to build full logic programming out of objects, with mixed results, and that a full implementation is a major undertaking, general enough that it says little about intent. His proposal is narrower. Most rules fall into a few special cases, so borrow only the concept: a specialised object that evaluates to a Boolean, a little truth test factored out as a Value Object, which can be asked about another object. That object is a Specification. It says what another object's state must be, and its most basic use is to test whether a given object satisfies the criteria.

Three details follow. Many specifications are simple tests like the delinquency rule; when rules are complicated, specifications can be combined as predicates are, which Chapter 10 develops. Because the rule is a full object, a Factory can build it from information found elsewhere, such as an account or a policy table, without coupling the object being tested to those sources. And a specification can carry what it needs: Evans's delinquency rule had its evaluation date built in, because each instance was created, used on some bills and discarded. He ends by calling a pattern a starting point, not a cookbook, and suggests skimming the implementation detail until you need it.

Now a model of the lesson's own: a seed bank that sends lots of seed to growers. A lot may go out when at least 85 percent of a test sample sprouts, its moisture is at most 8 percent, it is at most 10 years old, and it is not in quarantine. The listing writes that rule as a specification; the lot itself knows its measurements and nothing about the policy, and a Factory could read the thresholds from the bank's policy table.

interface LotSpecification { boolean isSatisfiedBy(SeedLot lot); }
// The seed bank's rule for sending a lot to growers, as a value object.
final class DistributableLot implements LotSpecification {
    private final int minGermination;   // percent of seeds that sprout
    private final int maxMoisture;      // percent water by weight
    private final int maxAgeYears;

    DistributableLot(int minGermination, int maxMoisture, int maxAgeYears) {
        this.minGermination = minGermination;
        this.maxMoisture = maxMoisture;
        this.maxAgeYears = maxAgeYears;
    }

    public boolean isSatisfiedBy(SeedLot lot) {
        return lot.germination() >= minGermination
            && lot.moisture() <= maxMoisture
            && lot.ageYears() <= maxAgeYears
            && !lot.inQuarantine();
    }
}

The lab takes the same rule as a list of clauses joined by and, and one candidate, and reports whether the candidate satisfies the rule, which clauses are true, the first false one in the order written, and every false one. On the preset lot-01 all 4 clauses are true and the lot may go out. On lot-02, germination 88, moisture 9, age 5, not quarantined, 3 clauses are true and the one false clause is moisture at most 8: the lot needs drying, not discarding. On lot-07, germination 72, moisture 10, age 11, three clauses are false, and the first is germination at least 85.

The order matters only for the first false clause, and the lab reports every false one as well, because a seed bank deciding whether to dry a lot, retest it or compost it needs all of them. That is a small version of Evans's argument: once the rule is an object, the question can be asked of any lot by any part of the system, and the answer comes with its reasons. The lab cannot say whether 85 percent is the right threshold; the bank's curators can.

How the lab counts. A specification is clauses attribute op value, with op one of = != < <= > >=, joined by and, or, not and parentheses (not binds tightest, then and, then or); a value is a number or a word beginning with a letter. Numbers compare exactly; a word compares only by = and != (an ordering op on a word is refused), and words compare exactly, letter case counted. A clause on an attribute the candidate lacks is false whatever its op, so not of it is true; an ordering clause on a word value is false. Clauses are numbered in the order written; the first false clause is the first in that order, whether or not the whole is satisfied.

Method

Checking one object against a specification

Four steps, the last of them on a system of your own.

1

Write the rule as clauses

State the rule as comparisons joined by and, each naming one attribute, an operator and a value.

2

Evaluate each clause

For the candidate, write true or false beside each clause, watching the boundaries: at least 85 admits 85, at most 10 refuses 11.

3

Give the verdict and its reasons

The candidate satisfies the rule only if every clause is true. Name the first false clause and every false one.

4

Do it on your own code

Find a Boolean method in a system you know that has grown past three conditions. Count its conditions, write the figure down, and write the name the specification would have.

Common mistakes

1
Putting every rule about an object on the objectA one-line test such as being past due belongs there. Evans's case is for rules that grow, that need an account's grace period, a policy table and a payment history: on the object they bury its meaning and drag in dependencies, and a Specification keeps them in the domain layer without that cost.
2
Thinking Specification means building a rule engineEvans warns that full logic programming in objects is a major undertaking and says too little about intent. The pattern borrows only the predicate: a small, special-purpose value object, often a simple test, combinable later when the rules require it.
3
Reading only the first false clauseThe first false clause depends on the order the rule was written in. On the lesson's illustration lot-07 fails three clauses, and a curator deciding what to do with it needs all three; the lab lists them for that reason.
