Huffman Codes

Section 16.3 compresses a file by giving frequent characters short codewords. Prefix codes, in which no codeword begins another, decode without ambiguity and are drawn as binary trees whose cost is the sum of frequency times depth. Huffman's algorithm merges the two lightest trees n − 1 times with a min-priority queue, in O(n lg n). One lemma shows the two rarest symbols can be siblings at the bottom of an optimal tree, another that merging them leaves a smaller problem of the same kind. Section 16.3 in six lines

Core ideas

What this lesson establishes

Three ideas: what makes a code decodable, what a code costs, and why the cheapest merge is safe.

1

Prefix code

A binary code in which no codeword is a prefix of another. Encoding concatenates codewords; decoding reads bits until they spell a codeword, emits it, and starts again, which is unambiguous because no longer codeword can begin the same way. The authors note that such codes lose nothing in compression against any other character code.

2

The code tree and its cost

A prefix code is a binary tree with the characters at the leaves, 0 for a left edge and 1 for a right. An optimal code's tree is full, with |C| leaves and |C| − 1 internal nodes. Its cost B(T) is the sum over characters of frequency times depth, the number of bits the file takes.

3

The greedy merge

Huffman's choice: take the two least frequent items, make them children of a new node whose frequency is their sum, and repeat. Each merge adds the sum of the two frequencies to the cost, so the rule always makes the cheapest merge available.

The material

Codes as trees, the merge, and two lemmas

Read Section 16.3 in your own copy first. The lesson sets out prefix codes and the cost in its own words, builds one code by hand, follows the two lemmas, and then lets the lab check the code against every tree.

“Huffman invented a greedy algorithm that constructs an optimal prefix code called a Huffman code.” The authors state it plainly in Section 16.3 and spend the rest of the section earning the word optimal. A prefix code, as a footnote concedes, would be better called prefix-free: no codeword is a prefix of another. This lesson reads the section.

The section begins with a file of characters and their frequencies. A fixed-length code spends the same number of bits on every character, three for an alphabet of six. A variable-length code gives frequent characters short codewords and rare ones long codewords, and the authors report typical savings of 20% to 90%, depending on the data. The catch is decoding: with variable lengths, where does one codeword end? Prefix codes answer it, since the first codeword of the encoded bits can always be recognised.

A prefix code is a binary tree: each character a leaf, each codeword the path from the root, 0 for left and 1 for right. These are not binary search trees; the leaves need not be in any order. An optimal code has a full tree, where every internal node has two children (Exercise 16.3-2): a node with one child could be removed, shortening every codeword below it. The number of bits for the file is B(T), the sum of c.freq · d(c) over the characters c, where d(c) is the depth of c's leaf and also the length of its codeword.

David Huffman found the algorithm, which the chapter notes date to 1952. HUFFMAN puts the characters in a min-priority queue keyed on frequency, then n − 1 times extracts the two least frequent items, makes them the children of a new node whose frequency is their sum, and inserts that node. The last item left is the root. With a binary min-heap each of the O(n) queue operations costs O(lg n), so the algorithm takes O(n lg n); the authors note a van Emde Boas tree would bring it to O(n lg lg n). Here is the algorithm on this lesson's six characters, with frequencies a:14, b:6, c:10, d:21, e:4, f:5, which total 60.

queue: e:4 f:5 b:6 c:10 a:14 d:21 merge e:4 + f:5 = 9 queue: b:6 9 c:10 a:14 d:21 merge b:6 + 9 = 15 queue: c:10 a:14 15 d:21 merge c:10 + a:14 = 24 queue: 15 d:21 24 merge 15 + d:21 = 36 queue: 24 36 merge 24 + 36 = 60 the root codeword lengths: a 2, c 2, d 2, b 3, e 4, f 4 B(T) = 14·2 + 10·2 + 21·2 + 6·3 + 4·4 + 5·4 = 144 bits = 9 + 15 + 24 + 36 + 60, the sum of the merges

So the code spends 144 bits on a file with these 60 characters, 12/5 = 2.4 bits a character against 3 for a fixed-length code. The last line is Exercise 16.3-4's identity: each merge pushes every leaf below it one level down, so the tree's cost is the sum of the merged frequencies, and Huffman's rule always chooses the cheapest merge on offer.

Theorem · Lemma 16.2, the greedy choice

If x and y are two characters of lowest frequency, some optimal prefix code gives x and y codewords of the same length that differ only in the last bit: they are sibling leaves at the greatest depth.

The proof is an exchange like Theorem 16.1's. Take any optimal tree and two sibling leaves a and b at its greatest depth. Swap x with a: x moves down, a moves up, and since x is no more frequent than a and a was no shallower than x, the cost does not rise. Swap y with b in the same way. The result is still optimal and has x and y as deepest siblings. Lemma 16.3 supplies optimal substructure: replace x and y by one new character z of frequency x.freq + y.freq; for any tree T′ for the smaller alphabet, splitting z's leaf into x and y gives a tree T with B(T) = B(T′) + x.freq + y.freq, so an optimal T′ yields an optimal T. Theorem 16.4 follows: HUFFMAN produces an optimal prefix code.

Method

Building a Huffman code by hand

Four steps build and price the code; the fifth is an alphabet of your own.

1

Queue the characters by frequency

Write every character with its frequency in increasing order.

2

Merge the two smallest

Remove the two smallest, write a new node with their sum, and put it back in order. Repeat until one node is left; there are n − 1 merges.

3

Read off the codeword lengths

Draw the tree from the merges: each merged pair are siblings under their sum. A character's codeword length is its depth.

4

Price the code two ways

Compute B(T) as the sum of frequency times depth, and again as the sum of the merged totals. They must agree.

5

Do it on an alphabet of your own

Count the letters of a short sentence of your own, build the code by hand, then type the counts and the sentence's letters as the message into the lab and compare your cost with its expected length times the total weight.

Why a fixed-length code is not optimal here

A three-bit code for six characters uses six of the eight codewords. Its tree has an internal node with only one child.

fixed: 000 001 010 011 100 101 no codeword starts 11, so the node for prefix 1 has one child (10) drop that node: 100 → 10, 101 → 11 two characters save a bit each the tree is still a prefix code

Any tree with a one-child node can be shortened this way, which is why an optimal code's tree is full. On the lesson's alphabet the fixed code costs 60·3 = 180 bits, the shortened one less, and Huffman's 144.

Common mistakes

1
Thinking a variable-length code needs separatorsIf no codeword is a prefix of another, the bits decode themselves: read until you have a codeword, emit it, carry on. The lab's round trip on the message faced returns it from 14 bits with nothing between the codewords. A code that needs separators is not a prefix code.
2
Merging by the original frequencies onlyAfter a merge the new node competes in the queue like any character. On the lesson's alphabet the second merge is b:6 with the new node 9, not b:6 with c:10; skipping the merged node gives a different tree that costs more.
3
Expecting Huffman to compress every fileThe saving comes from unequal frequencies. With equal weights the lab's uniform preset gives every symbol two bits, the same as a fixed-length code, and Exercise 16.3-8 shows that nearly equal frequencies over 256 characters cannot beat eight bits. The algorithm is optimal; the optimum may save nothing.
