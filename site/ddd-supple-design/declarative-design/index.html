Declarative Design

Declarative design promises a program that is its own specification, and Evans has seen many attempts at it trap the model in the limits of a framework. Read his account of its pitfalls, of domain-specific languages, and of the declarative style a supple design makes possible; then ask whether one storage rule subsumes another, and find the candidates that separate them.

Declarative Design in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson. The first two are Evans's, the third the lab's.

1

Declarative design

Writing a program, or part of one, as a kind of executable specification: a precise description of properties that actually controls the software, through reflection or code generation, so that the declaration can be taken at face value.

2

Subsumption

A more stringent specification subsumes a less stringent one: anything that satisfies it satisfies the other too, so it could take the other's place without dropping a requirement. Viewed as predicates, it is logical implication.

3

A separating candidate

A candidate that satisfies one specification and not the other. The lab checks the candidates it is given; one separating candidate disproves subsumption, and none among those given proves nothing on its own.

The material

The promise, its pitfalls, then two rules compared

Read the sections Declarative Design, Domain-Specific Languages, A Declarative Style of Design and Extending Specifications in a Declarative Style in Chapter 10 first. The lesson reads them as an argument, then compares two specifications on a set of candidates.

“A supple design can make it possible for the client code to use a declarative style of design.” That is from A Declarative Style of Design, in Chapter 10. This lesson reads it with the sections around it, from Declarative Design to Extending Specifications in a Declarative Style. Read them in your own copy first; the Specification lesson of the course Breakthroughs and Implicit Concepts set out the pattern they extend.

Evans begins with what the other patterns cannot do. Assertions help, but handwritten code can always have a side effect nobody excluded, and much code is boilerplate that adds no meaning and buries the model. Declarative design answers with a precise description that actually controls the software, through reflection or through code generated from the declaration, so that another developer can take it at face value. He calls generating a running program from the model's properties a kind of Holy Grail, and names two problems he has met more than once: a declaration language that cannot say everything needed inside a framework that makes it hard to go beyond it, and code generation that mixes generated and handwritten code so that regenerating destroys work. The common result, he says, is a model dumbed down to fit the tool.

Rule engines are declarative in principle, but control predicates added for performance bring side effects back, so that reordering rules can change results. Many declarative approaches fail when developers go round them. The greatest value he has seen comes from a narrowly scoped framework that automates one tedious, error-prone part of a design, object-relational mapping for one, and leaves the rest free. Domain-specific languages make the strongest link to the Ubiquitous Language, but refining the model then means changing a language, which takes skills a team, and the team after it, may lack; he notes that in a functional language such as Scheme the style comes without splitting the system in two.

Then the turn. A design with intention-revealing interfaces, functions and assertions is already edging into declarative territory: its elements say what they mean and have known effects or none. The book shows it on Specification, which is an adaptation of the predicate. Predicates combine with and, or and not, and those operations are closed under predicates, so combined specifications show Closure of Operations. Below is the idea in Java 8, written for this lesson: each combinator returns a new Spec and changes nothing.

// Java 8: a specification whose and, or and not are closed under Spec.
interface Spec<T> {
    boolean isSatisfiedBy(T candidate);

    default Spec<T> and(Spec<T> other) {
        return c -> isSatisfiedBy(c) && other.isSatisfiedBy(c);
    }
    default Spec<T> or(Spec<T> other) {
        return c -> isSatisfiedBy(c) || other.isSatisfiedBy(c);
    }
    default Spec<T> not() {
        return c -> !isSatisfiedBy(c);
    }
}

Evans is careful about cost. His own implementation is meant to explain, and on one project a more elaborate version made millions of small objects that slowed an object database, so he shows another that encodes the expression and interprets it. Often the full set is not needed, and and is used far more than the others: “Don't be afraid to implement only AND, if that is all you need.” Java 8 itself now gives java.util.function.Predicate the methods and, or and negate, so the combinators come free; the next operation does not.

Subsumption, which Evans says is seldom needed and hard to implement, compares two specifications. His case is a regulation that tightens: the users want the kinds of goods whose handling became more stringent, and validating today's stock will miss any kind not now in stock. A stricter specification subsumes a looser one if everything satisfying it satisfies the other. Proving it in general is hard; special cases are easy. A threshold specification compares thresholds, and with and alone one conjunction subsumes another when its clauses include all of the other's. With or and not the proofs become much harder, and he advises choosing: forgo some operators or forgo subsumption.

The lab's model is a seed bank written for this lesson, whose storage rule has been tightened, and five stored lots, lotA to lotE. One warning before you run it. The lab never says subsumes, because the word runs both ways: its rules note that logicians say the looser rule subsumes the stricter, while Evans says the stricter subsumes the looser. Its tiles ask one plain question: does A accept every candidate B accepts? A yes means, in Evans's words, that B subsumes A. So to ask Evans's question, whether the new rule subsumes the old, enter the old rule as A and the new one as B. The lab's counter-examples are the separating candidates of this lesson: they satisfy B and fail A.

old rule:  moisture <= 8 and temp <= -10
new rule:  moisture <= 6 and temp <= -18 and sealed = yes

On the preset tightened, A is the old rule and B the new. Only lotA satisfies B, while 4 lots, lotA to lotD, satisfy A; lotA satisfies both, so there are 0 counter-examples. Both rules are conjunctions of comparisons, so the lab also gives the logical answer, yes, for every candidate and not only these five: a moisture of at most 6 is at most 8, a temperature at most −18 is at most −10, and the old rule asks nothing about sealing. In Evans's terms, the new rule subsumes the old.

On the preset loosened the rules swap places, which asks whether the old rule subsumes the new. No: 3 counter-examples, lotB, lotC and lotD, satisfy the old rule and fail the new, each for a different clause, and the logical answer says the old rule allows a moisture that fails the new rule's clause moisture <= 6. lotE satisfies neither. Those three are the lots whose storage the tightening affects, the partial report Evans describes; the logical answer holds whatever happens to be in stock.

On the preset with-or, B is a rule with an or, (moisture <= 6 and sealed = yes) or temp <= -25. Of the five lots, lotA and lotC satisfy it, and both satisfy the old rule, so there are 0 counter-examples among them; but B is not a pure conjunction, and the lab says the logical answer is not decidable by it. The answer is in fact no: a sealed lot at moisture 4 kept at 0 degrees satisfies B and fails the old rule. Add it as lotF and the lab finds it.

loyalMember:     visits >= 10 and member = yes

Two rules for a theatre's loyalty discount. Say which rule subsumes the other in Evans's sense, and give one candidate that satisfies one rule and not the other. Then enter the rules and a few candidates in the lab, including yours, minding which rule goes in as A. Separate candidates with semicolons, as in ann, visits=12, member=yes; bo, visits=3, member=no.

How the lab counts. A specification is clauses attribute op value, with op one of = != < <= > >=, joined by and, or, not and parentheses (not binds tightest, then and, then or); a value is a number or a word beginning with a letter. Numbers compare exactly; a word compares only by = and != (an ordering op on a word is refused), and words compare exactly, letter case counted. A clause on an attribute the candidate lacks is false whatever its op, so not of it is true; an ordering clause on a word value is false. The question is one relation, in plain words: does A accept every candidate B accepts? The word subsumes is used both ways round: in the logicians' sense the looser rule, A, subsumes B; in Evans's sense (Chapter 10) the stricter rule, B, subsumes A. The tiles avoid the word. On the candidates the relation is checked one by one. For every possible candidate the answer is exact when both are clauses joined only by and: B's clauses on each attribute give the values it allows (an interval of numbers less excluded points, and words), and A accepts all B accepts when B allows nothing or every clause of A holds for everything B allows, an attribute B never mentions being allowed missing. With or or not in either, the lab says it cannot decide.

Method

Comparing two specifications

Four steps, the last of them on rules of your own.

1

Write both as clauses

Write each rule as clauses joined by and, or and not, each clause an attribute, a comparison and a value.

2

Compare clause by clause

For two conjunctions, check that every clause of the looser rule is implied by some clause of the stricter one on the same attribute.

3

Look for a separating candidate

Write a candidate that satisfies one rule and fails the other, choosing each attribute at the edge of a clause.

4

Do it on rules of your own

Find a rule in a system you know that was tightened, write the old and the new as specifications, and say whether the new one subsumes the old. Give the candidate that shows it if it does not.

Common mistakes

1
Taking declarative design to mean generating the whole program from declarationsEvans calls that a Holy Grail with pitfalls he has met repeatedly, and says the greatest value he has seen is a narrow framework that automates one tedious part, such as object-relational mapping. The declarative style he recommends comes from the chapter's own patterns, as specifications combined with and, or and not.
2
Building every operator because the pattern describes itEvans says that and is used far more than the others and is simpler to implement, that one need not be afraid to implement only and, and that using a pattern does not mean building features you do not need. Subsumption, especially with or and not, he advises against unless the benefit justifies the difficulty.
3
Reading no separating candidate as proof of subsumptionThe lab checks the candidates it is given. On the lesson's illustration, the rule with an or has no separating candidate among the five lots and still does not subsume the old rule; a sixth lot shows it. Only for pure conjunctions does the lab give a logical answer.
