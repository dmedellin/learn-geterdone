Assertions

Assertions in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson, all from the design-by-contract school that Evans draws on.

1

Post-condition

A statement of the outcome an operation guarantees: the state it leaves behind, including its side effects. If you trust it, Evans says, you need not read how the method works.

2

Precondition

A condition that must hold before the call for the post-condition to be guaranteed; Evans compares it to the fine print of a contract. A call that breaks it is owed nothing.

3

Invariant

A statement about an object's state that is true at the end of every operation. Evans adds that invariants can be declared for a whole Aggregate, where they define its integrity rules.

The material

The argument, the pattern, then the state a command leaves

Read the section Assertions in Chapter 10 first. The lesson reads the argument, states the pattern as a tool, and then checks the state one command leaves against what it promises.

“If you trust the guarantee of a post-condition, you don't have to worry about how a method works.” That sentence is from the section Assertions, the third pattern of Chapter 10. Read it in your own copy first.

Side-Effect-Free Functions cut the problem down, Evans says, but leave commands on the entities, and anyone calling them has to understand their consequences. A command with no complex computation can be read by inspection. But in a design built from smaller parts, a command calls other commands, and the caller must understand each of them, which defeats encapsulation. And since an interface does not restrict side effects, two classes implementing it can change different things, which defeats the point of abstraction and polymorphism. When effects are defined only by the code, the only way to understand the program is to trace execution along its branches.

Intention-revealing names help, but informal hints are not always enough. Evans turns to the design-by-contract school, described in Bertrand Meyer's book of 1988. A post-condition describes the guaranteed outcome of a call, side effects included; a precondition is what must hold for that guarantee; a class invariant is true of an object whenever any operation finishes, and an invariant can cover a whole Aggregate. All of them describe state rather than procedure, which is why they are easier to analyse, and the effects of delegation are already folded into them.

As a tool: state the post-conditions of operations and the invariants of classes and aggregates. Where the language cannot express them, check them with automated tests, and record them wherever the team's process keeps such things. Because assertions are about state, the tests are easy to write: set up the preconditions, run the operation, check the post-conditions. Evans adds a caution about people: any consistent set of assertions would serve a compiler, but developers extrapolate from the concepts of the model, so seek a model whose assertions they could have guessed.

The book's example returns to paint. Mixing one paint into another adds the second's volume to the first and leaves the second unchanged, a post-condition that does not fit anyone's idea of paint. The obvious fix, emptying the second paint, turns out to break a requirement the original designers knew about. Rather than document the odd post-condition, Evans takes the awkwardness as a sign of a missing concept and splits the class, so that the one remaining command does something any reader would expect and the assertions become common sense.

Now a command written for this lesson, from a bike-share scheme that moves bikes between docks to rebalance them. The comment states its post-condition, the class invariant and the precondition, and the test after it does what Evans describes: precondition, call, post-condition.

// In Dock, an entity. After a.sendBikesTo(b, n):
//   a holds n bikes fewer than before, and b holds n more;
//   so the two docks together hold as many bikes as before.
// Invariant of every Dock: 0 <= bikes() and bikes() <= capacity().
// Precondition: n <= bikes() and n <= b.spaces().
void sendBikesTo(Dock other, int n) {
    bikes = bikes - n;
    other.receive(n);
}
// The test sets up the precondition, acts, and checks the state.
Dock a = new Dock(12, 8);   // capacity 12, holding 8
Dock b = new Dock(10, 5);   // capacity 10, holding 5
a.sendBikesTo(b, 3);
assertEquals(5, a.bikes());
assertEquals(8, b.bikes());

The lab checks a stated state against the assertions written as one specification. Each candidate is the state after a.sendBikesTo(b, 3): removed and added are the bikes taken from a and given to b, fromBikes is what a holds after, and toSpaces is the room left in b. The specification below is the post-condition, then the two invariants that could break. On the preset transfer-kept every clause holds, 4 of 4, and the specification is satisfied.

removed = 3 and added = 3 and fromBikes >= 0 and toSpaces >= 0

On the preset transfer-overfull, b started with only 2 spaces. The post-condition's two clauses hold, but toSpaces is −1, and the first false clause is toSpaces >= 0, the only entry in the lab's list of every false clause: the invariant is broken. The operation did what it promised, and the caller broke the precondition that n fit in b. That is the fine print doing its work: it says whose fault the broken invariant is.

On the preset transfer-one-sided, an implementation forgot the first line and never took the bikes out of a. Its removed is 0, the first false clause is removed = 3, and the other three clauses hold. Bikes have been created out of nothing, and only the stated post-condition notices; nothing in the method's name would have.

Exercise

// After vault.withdraw(80), from 100 packets, reorder level 30:
// post-condition:  taken = 80 and left = 20
// invariant:       left >= 30 or reorder = yes
state A:  taken=80  left=20   reorder=yes
state B:  taken=80  left=20   reorder=no
state C:  taken=80  left=100  reorder=no

A seed bank's vault holds 100 packets of a variety and must be flagged for reordering whenever fewer than 30 are left. For each state after withdraw(80), say whether the assertions hold and, if not, the first clause in the written order that is false. Then type the three states into the lab as candidates to check, one record each, separated by semicolons: A, taken=80, left=20, reorder=yes; B, ….

How the lab counts. A specification is clauses attribute op value, with op one of = != < <= > >=, joined by and, or, not and parentheses (not binds tightest, then and, then or); a value is a number or a word beginning with a letter. Numbers compare exactly; a word compares only by = and != (an ordering op on a word is refused), and words compare exactly, letter case counted. A clause on an attribute the candidate lacks is false whatever its op, so not of it is true; an ordering clause on a word value is false. Clauses are numbered in the order written; the first false clause is the first in that order, whether or not the whole is satisfied.

Method

Stating what a command guarantees

Five steps, the last of them on code of your own.

1

Name the state

List the quantities a command changes and the ones it must not, on the receiver and on any argument.

2

Write the post-condition

State, without saying how, what each of those quantities is after the call in terms of what it was before.

3

Write the invariants and the precondition

State what must be true of every object of the class after any operation, and what the caller must ensure for the post-condition to hold.

4

Turn them into a test

Set up the precondition, make the call, and assert each clause; check the state a faulty implementation would leave, clause by clause, in the lab.

5

Do it on your own code

Pick a command in a system you know that changes two objects. Write its post-condition and one invariant as a test, and note whether the assertion reads as common sense or needs explaining. If it needs explaining, say what concept might be missing.

Common mistakes

1
Thinking assertions need a language that checks themEvans wrote when few object languages supported assertions, and says they are still a powerful way to think about a design. Where they cannot be coded, unit tests stand in: the setup puts the preconditions in place and the test checks the post-conditions after the call. The lesson's dock test is one.
2
Fixing an awkward post-condition by making the code match intuitionIn the paint example the intuitive fix broke a requirement the original designers had kept. Evans neither forces the fix nor settles for documenting the oddity; he reads the awkwardness as a sign of a missing concept and finds a model in which the assertions make sense. Sometimes, he grants, the odd post-condition documented is the best answer.
3
Reading satisfied assertions as proof that an operation is correctAssertions say only what they say. Evans opens Declarative Design by noting that handwritten code can still have side effects that no assertion excluded. On the lesson's illustration, a transfer that also cleared a dock's maintenance flag would satisfy all four clauses.

Finish when you can state a command's guarantee and check a state against it.

Given a command, write its post-condition, a class invariant and its precondition, and say for a stated result which clause, if any, fails first.

Note: The lab checks one stated state against one stated set of clauses. It does not run the operation, so it cannot find a state the code might leave that nobody wrote down, and it cannot say whether the assertions are the right ones for the domain, which is the question Evans's paint example turns on.
