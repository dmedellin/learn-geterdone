Aggregate Invariants and Concurrent Change

The Aggregates pattern's own example: two users edit different parts of one order, each keeps the order's limit, and together they break it. Read how Evans moves from object locks to a lock on the whole aggregate and then to a better model, and run concurrent edits to a class booking under both schemes.

Invariants and locks in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson. The first is Evans's; the other two are the lab's names for the two locking schemes the example compares.

1

Invariant

A consistency rule that must hold whenever the data changes. The lesson's is a sum: the places taken by the parties in a class may not exceed the places it has.

2

Object lock

A scheme that locks only the object a user is editing. Two users editing different objects never wait for each other, and never see each other's edit before they commit.

3

Aggregate lock

A scheme that locks the whole aggregate, through its root, as soon as one user begins to edit anything inside it. A second user who tries to edit the same aggregate is refused until the first is done.

The material

The example's argument, then the two schemes counted

Read the Aggregates pattern's example, from the purchase-order model to the price copied into each line, in your own copy first.

“We need to find a model that leaves high-contention points looser and strict invariants tighter.” Evans sets this as the goal before the Aggregates pattern's rules, and the pattern's extended example shows what it means. This lesson reads that example, in which every step is a reasonable locking scheme and every step but the last goes wrong.

The example is a purchase order broken into line items, each for a quantity of a catalogue part, under one rule: the items' total may not pass the order's approval limit. The first scheme locks only the object a user starts to edit. Two buyers then change two different lines of the same order; each checks the total against the limit in their own copy and is within it; neither line is locked by the other; both commit, and the stored order is over its limit with no one aware. Locking the whole order would have refused the second save.

Evans then pushes further. A part's price can change too, which would break the rule from another direction, so he tries locking the parts as well, and the users begin to wait on one another over popular parts and finally deadlock. The way out is not a cleverer lock but more knowledge of the business: parts appear in many orders, parts change less often than orders, and a price change need not reach orders already placed. So the price is copied into each line when it is added, the line no longer depends on the part's current price, and the order and its lines become one aggregate whose limit can be enforced.

Two things are worth noticing in that last step. The rule that stays strict, the limit, is now wholly inside one boundary. The rule that was loosened, keeping old orders in step with new prices, did not vanish; Evans suggests a daily list of items with outdated prices for users to update or let stand. And the ownership matches the business, since an order and its lines are created and deleted together while parts come and go on their own.

The Enterprise Application Patterns lesson Pessimistic and Coarse-Grained Locks reads the mechanism of a lock on a group, with its version counters and shared locks. Evans's emphasis is earlier: which objects form the group is a decision about the model, and once the aggregate is drawn the lock follows it.

The lab's instance is a cookery school's Saturday class with 12 places, booked by three parties: the Walshes with 4, the Okafors with 3 and the Lins with 2, 9 places in all. The class is the root, and its resize method checks the rule in memory. Two staff members, Pat and Sam, each read the class at minute 0. Pat makes the Okafors 5 at minute 1 and 6 at minute 4, and Sam makes the Lins 4 at minute 2. In Pat's copy the sum is 12; in Sam's it is 11. Each passes the check.

// One class session; the parties booked into it are inside its boundary.
public class CookeryClass {
    private final ClassId id;
    private final int places;
    private final Map<PartyName, Integer> parties = new HashMap<>();

    public void resize(PartyName party, int people) {
        int others = taken() - parties.getOrDefault(party, 0);
        if (others + people > places) {
            throw new IllegalArgumentException("over " + places + " places");
        }
        parties.put(party, people);
    }

    int taken() {
        return parties.values().stream().mapToInt(Integer::intValue).sum();
    }
}

On object-locks Pat locks the Okafors' line and Sam the Lins', so neither waits: 2 users commit and 0 are refused. The final values are 4, 6 and 4, and the lab reports a final sum of 14 against a limit of 12, so the invariant does not hold. Neither user did anything wrong, and the root's check ran both times, each time on a copy that did not contain the other edit. The last tile, edits lost, counts committed values that a later commit overwrote: 0, because the two changed different parties.

On aggregate-lock Pat's first edit at minute 1 takes the whole class. Sam's edit at minute 2 is refused, so 1 user commits and 1 is refused, and Sam's edit is discarded until Sam reads the class again. The final values are 4, 6 and 2, the sum is 12, and the invariant holds. The price is the refusal itself: Sam was changing a different party and still had to wait.

The preset same-party is the case object locks do catch. Both staff edit the Okafors, so under object locks the second to edit is refused on the same line: Pat alone commits and the sum stays at 12. Object locks protect a rule about one object; the trouble starts when the rule is about the sum of several.

Exercise

  • A guided walk with a limit of 15 walkers. Parties: ana 6, ben 5, cho 2.
  • Edits (minute, user, party, new size): 1, kim, cho, 3; 2, lee, ben, 6; 3, kim, cho, 4.

Each user reads at minute 0 and commits at their last minute. Work out, under object locks and then under an aggregate lock, who commits, the final sizes, the final sum, and whether the limit holds. Then set the scheme in the lab and check both.

How the lab counts. Every user reads the aggregate at minute 0, edits items at the minutes given (an edit sets the item's new value) and commits at their last edit's minute. Locks are pessimistic, taken at an edit and held to the end of the user's commit minute. Object scheme: an edit locks only its item, so two users conflict only on the same item. Aggregate scheme: an edit locks the whole aggregate. An edit of what another user holds refuses its user outright: all their edits are discarded and their locks released. Edits are taken in minute order, ties in record order; commits apply in commit-minute order, ties in order of first appearance. An edit lost is a committed value overwritten by a later commit. The invariant is that the sum of the values is at most the limit.

Method

Running concurrent edits by hand

Four steps, the last of them on a rule of your own.

1

Give each user a copy

Write down what each user reads at the start. Every check that user makes is against that copy plus their own edits, not the others'.

2

Apply the locking scheme

Under object locks, refuse a user only on an object another user is already editing. Under an aggregate lock, the first user to edit anything holds the whole aggregate, and every other editor is refused.

3

Combine what commits

Apply every committed edit to the stored values, then check the invariant on the result, not on any one user's copy.

4

Do it on your own rule

Find a rule in a system you know that sums or compares several records, such as a budget or a capacity. Write two edits that each keep it and together break it, and say which object the lock should be on.

Common mistakes

1
Believing that if every edit checks the rule, the rule is safeIn the example each user's check passes and the stored order still breaks the limit, because each check sees only that user's copy. The rule spans several objects, so it is only as safe as the scope of the lock. On the lesson's illustration, two passing checks under object locks give a stored sum of 14 against 12.
2
Concluding that the safest design locks everything the rule touchesEvans tries exactly that, locking the parts as well as the order, and it ends in contention and deadlock. His answer is to change the model, copying the price so the parts fall outside the boundary, not to widen the lock.
3
Treating an aggregate lock as freeEvans says a lock on the whole order may suit work spread across many small orders and become cumbersome when many people edit lines of one large order. On the lesson's illustration Sam is refused although Sam was changing a different party.

Note: The lab's model of locking is the example's simplest one: each user reads at the start, locks on first edit and commits at the end. It does not model waiting, retries, version checks or deadlock, and it cannot weigh refused edits against broken rules. That weighing is the business knowledge Evans asks for.
