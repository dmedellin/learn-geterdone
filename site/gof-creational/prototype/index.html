Prototype

Prototype makes new objects by asking a sample instance to copy itself, which removes the factory classes and brings what the authors call its hardest part, implementing the copy correctly, and with it the question of what a clone shares. Prototype in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson, all of them the pattern's.

1

Prototype

An instance kept as a sample of what to create. A client makes new objects by asking it to copy itself, so the client needs neither the product's class nor a factory class for it.

2

Prototype manager

A registry that stores prototypes under keys, so that clients can register, look up, replace and remove them while the program runs, and clone by name.

3

Shallow and deep copy

A shallow copy duplicates the object and shares everything it refers to with the original; a deep copy duplicates those parts as well, so original and clone are independent. Cloning makes you choose, part by part, what is shared.

The material

The pattern first, then the count

Read Prototype in your own copy first. The lesson reads it as a tool, section by section, and then counts who shares what after cloning.

“Specify the kinds of objects to create using a prototypical instance, and create new objects by copying this prototype.” That is the intent of Prototype, the fourth pattern of Chapter 3 and an object creational pattern. Read it in your own copy first. The lesson reads it as a tool, then turns to what the authors call the pattern's hardest part, implementing the clone operation correctly, and to the question inside it of what a clone shares with its prototype, and counts who sees a change made through one clone.

The book's example is a music score editor built by customising a general framework for graphical editors. The framework supplies a tool class that creates a graphic and adds it to the document, but it cannot know the application's note and staff classes, and a subclass of the tool for every kind of note would multiply classes that differ only in what they make. So each palette tool is an instance of the one tool class, given a different prototype graphic to clone. The authors then go further: whole notes and half notes need not be classes at all, but instances of one note class with different images and durations, each installed as a prototype.

Prototype applies when a system should not care how its products are made and, besides, when the classes to create are known only at run time, loaded dynamically for instance; when you want no factory classes shadowing the product classes one for one; or when a class's instances come in only a few combinations of state, so that keeping one prototype per combination is simpler than setting the state by hand each time. The participants are the Prototype, which declares the operation that copies it; the ConcretePrototypes, which implement it; and the Client, which asks a prototype for a copy of itself whenever it needs a new object.

// A playlist template and its two ways of being copied.
final class Playlist {
    private final String name;
    private final List<Track> tracks;      // a part that can change

    Playlist(String name, List<Track> tracks) {
        this.name = name;
        this.tracks = tracks;
    }

    Playlist shallowCopy(String newName) {
        return new Playlist(newName, tracks);                    // shares it
    }

    Playlist deepCopy(String newName) {
        return new Playlist(newName, new ArrayList<>(tracks));   // owns one
    }

    void add(Track track) { tracks.add(track); }
}

Prototype shares the main consequences of Abstract Factory and Builder: it keeps the concrete product classes out of the client's sight, so the client knows fewer names, and lets a client work with application-specific classes unchanged. The authors add five of its own. Products can be added and removed while the program runs, by registering a prototype. New kinds of object can be specified by values rather than new classes, which lets users define something close to new classes without programming. New objects can be specified by structure, as when a circuit editor offers a user's subcircuit as a palette item, provided the clone is deep. Subclassing is reduced, since no Creator hierarchy is needed, a gain mostly in C++ and other languages in which a class is not an object. And an application can be configured with classes loaded while it runs. The main liability is that every prototype class must implement cloning, which is hard to add to classes that already exist, and hard when they hold objects that cannot be copied or that refer to each other in a cycle.

“Cloning forces you to decide what if anything will be shared.” That sentence closes the authors' discussion of shallow and deep copying, the second of three implementation issues. A shallow copy, Smalltalk's default and what C++'s default memberwise copy gives, shares every referenced part between original and clone; it is simple and often enough. A prototype with structure usually needs a deep copy, so that the clone's parts are clones of the prototype's parts, and saving an object and loading it straight back is one way to get one. The first issue is the prototype manager, a store keyed by name with operations to register and unregister, which clients can change and browse at run time. The third is initialising clones: a uniform clone operation cannot take arguments, so clients reset state after cloning, through existing setters or a separate initialise operation. Java's own Object.clone copies fields one for one, a shallow copy, which is why the sketch writes both copies out.

// A prototype manager: templates by key, copied on request.
final class Templates {
    private final Map<String, Playlist> byKey = new HashMap<>();

    void register(String key, Playlist prototype) { byKey.put(key, prototype); }

    void unregister(String key) { byKey.remove(key); }

    Playlist create(String key, String newName) {
        Playlist prototype = byKey.get(key);
        if (prototype == null) {
            throw new IllegalArgumentException("no template " + key);
        }
        return prototype.deepCopy(newName);
    }
}

The Sample Code makes a maze factory that is given a prototype maze, room, wall and door and clones them, so a new kind of maze is a new set of prototypes rather than a new factory subclass; a cloned door is then given its rooms by an initialise operation, and a Smalltalk version keeps a dictionary of prototypes. Read it in the book. The known uses reach back to Ivan Sutherland's Sketchpad and to ThingLab; Goldberg and Robson name prototypes as a pattern and Coplien describes C++ idioms for them; the etgdb debugger front end clones the debugger adaptor an environment variable names; Mode Composer keeps interaction techniques as prototypes; and the music editor is based on Unidraw. The related patterns: Prototype competes with Abstract Factory in some designs, the subject of the chapter's discussion, and can serve it, a factory holding prototypes to clone; and designs heavy with Composite and Decorator often gain from it.

Now the lab, on a music playlist app rather than a score editor. A template playlist, a workout mix, is the prototype, and three runners clone it. The lab's sharing view asks who holds which track list and what a change made through one holder reaches; its panel speaks of a model, a value and holders, which here are the design, the track list and the template with its clones. On the preset shallow-clones the copies are shallow, so the template and all three clones hold the one list tracks-w. Ben adds a track through his copy: the lab counts 4 holders, 4 that see the change, 3 surprised, the template, Ana and Cy, who saw a change they did not make, and 0 new values. The template is among the surprised, so every clone made from it later starts with Ben's track.

On deep-clones each copy has its own list, and Ben's change to tracks-b reaches 1 holder, himself, with none surprised: the clones are independent, at the price of a list copied for every clone, which this view does not count. The preset shallow-immutable shares one list again, but an immutable one: a change made through Ben gives him a new list, tracks-w′ in the lab, so 1 holder sees it, none are surprised, and 1 new value is made. A shallow copy is safe for any part that cannot change, which is why the decision the authors describe is made part by part.

Method

Making new objects by copying

Four steps, the last of them on code of your own.

1

Find the classes that differ only in values

Look for subclasses, or factory subclasses, whose only job is to set different values. Each could be one class with a prototype per variant.

2

Decide part by part what a clone shares

For each field of the prototype, ask whether it can change after cloning. Share what cannot; copy what can.

3

Register the prototypes

Keep the prototypes in a manager keyed by name, so that a new variant is registered while the program runs instead of written as a class.

4

Do it on your own code

Find an object in a system you know that is copied to make new ones: a template, a default configuration, a test fixture. List who holds its changeable parts after copying, type them into the lab, and count the holders one change surprises.

Common mistakes

1
Assuming a copy is independent of its prototypeA shallow copy shares every part the prototype refers to. On the playlist the lab counts 3 holders surprised by one runner's change, the template among them, so every later clone inherits it. The authors put it plainly: cloning makes you decide what is shared.
2
Deep-copying everything to be safeA deep copy costs an object per part for every clone, and is wrong for parts meant to be shared, such as a connection to a service. A part that cannot change can be shared by a shallow copy, as the immutable preset shows.
3
Passing initial values through the clone operationPrototypes of different classes need different values, so a clone operation with parameters cannot be uniform. The authors reset state after cloning, through setters or an initialise operation.
