Singleton

Singleton makes a class responsible for having exactly one instance and for handing it out. Core ideas

What this lesson establishes

Three terms carry the lesson. The first is the pattern; the other two come from its implementation section.

1

Singleton

A class that makes sure it has one instance and gives every client one well-known way to reach it, through a class operation rather than a global variable.

2

Lazy initialisation

Creating the instance the first time it is asked for, not when the program starts. The instance is made only if it is used, and with whatever the program knows by then.

3

Registry of singletons

A well-known table in which singleton classes register their instance by name, so the access operation can hand out the one chosen at run time without listing every possible subclass.

The material

The pattern first, then the count

Read Singleton in your own copy first. The lesson reads it as a tool, sets its benefits beside its costs, and then counts instances and cost.

“Ensure a class only has one instance, and provide a global point of access to it.” That is the intent of Singleton, the last pattern of Chapter 3 and an object creational pattern. Read it in your own copy first. The lesson reads it as a tool, sets its benefits beside the costs its implementation section admits, and counts the instances and the cost a run of requests adds up to with one shared instance and without.

The motivation is a short list of things a system should have only one of: one printer spooler however many printers, one file system, one window manager, one company served by an accounting system. A global variable makes an object easy to reach but does nothing to stop a second one being made. The authors' answer is to make the class itself responsible: it keeps track of its sole instance, intercepts requests to create new ones, and offers a way to get the one it has.

Singleton fits, in the authors' list, when a second instance would be an error and every client needs one known place to find the first, and when that one object may later belong to a subclass, chosen without touching the clients' code. There is one participant, the Singleton class, with an Instance operation that is a class operation, a static method in Java as in C++, and that may create the instance itself. Clients reach the instance only through that operation.

// One registry of lockers, made on first use and shared.
final class LockerRegistry {
    private static LockerRegistry instance;   // none until asked for

    private LockerRegistry() {                // no client can call new
        loadBanksFromDisk();                  // the cost, paid once
    }

    static synchronized LockerRegistry instance() {
        if (instance == null) {
            instance = new LockerRegistry();
        }
        return instance;
    }

    private void loadBanksFromDisk() {
        // read every bank's doors and sizes
    }
}

The authors list five benefits. Access to the sole instance is controlled, because the class holds it. The name space is reduced, an improvement on global variables that would each hold a sole instance. Operations and representation can be refined, by subclassing the Singleton and configuring the application with the subclass's instance. A variable number of instances is easy, since only the access operation changes if you later want two, or a fixed pool. And the pattern is more flexible than class operations, static methods, which make that change hard and which in C++ are never virtual, so a subclass cannot override them.

The costs are in the implementation section. To ensure a unique instance the constructor is hidden, protected in the book's C++ and private here, and the class operation creates the instance lazily, on first access. The authors explain why a C++ global or static object will not do: nothing stops a second one being declared, the values it needs may not be known when static objects are initialised, and C++ fixes no order of initialisation across files, so singletons that depend on each other fail; and a static object forces every singleton to be made whether used or not. Subclassing is harder still. Choosing the subclass inside the access operation with conditionals hard-wires the set of subclasses; choosing at link time fixes it before the program runs; a registry, in which each singleton registers itself by name, frees the access operation from knowing the subclasses, but only if every candidate is created so that it can register. The section does not discuss threads; in Java the lazy check must be safe for them, which is why the sketch's method is synchronized.

The Sample Code makes the maze factory of the Abstract Factory lesson a singleton, first with no subclasses and then choosing the bombed or enchanted subclass from an environment variable inside the access operation, and the authors point out that the operation must then be edited for every new subclass, which a registry would avoid. Read it in the book. The known uses are Smalltalk-80's current change set; the metaclasses of Smalltalk, each the class of one class and with exactly one instance; and InterViews's Session and WidgetKit, the second an abstract factory whose subclass is chosen from an environment variable. Related Patterns says only that many patterns can be built with Singleton, naming Abstract Factory, Builder and Prototype.

Singleton is also the pattern in the catalog most argued over since. A common later view holds that a singleton reached through a static operation is global state under another name: every class that calls it depends on it without saying so, and a test cannot easily put a different instance in its place, so many designs now create the one instance at start-up and pass it to the objects that need it. The authors' text meets part of this, in the registry and in the benefit that only the access operation must change to allow more instances; it does not discuss testing. Read both, and weigh them against the design in front of you.

Now the lab, on a parcel locker network rather than a printer spooler. Its registry of locker banks costs 50 to load from disk and its audit log costs 20 to open; five requests reach the registry in turn, from a kiosk, the app, a courier, the kiosk again and a night job, and none reaches the log. The access view counts the requests, the instances created, the cost at the start, the cost in all, the subjects never requested, the instances alive at the end and the first request's cost. On registry-fresh, where every request constructs its own registry, there are 5 requests, 5 instances created and still alive, a cost of 250, and the log is the 1 subject never requested.

On registry-lazy, the sketch above, the first request creates the registry and the other four reuse it: 1 instance, a cost of 50, nothing paid at the start, and the first request pays the 50. On registry-eager, the static-object approach the authors argue against, both objects are made before any request: 2 instances, 70 paid at the start and 70 in all, the first request's cost 0, and the log made though no one asks for it, the small liability the authors name. The comparison tile sets the three schemes side by side: eager 70, lazy 50, fresh 250. The count of requests refused belongs to the Proxy lesson in the next course and is 0 here, since no access rights are stated.

How the lab counts. Eager creates every subject at the start; lazy (a virtual proxy, or a singleton made on first use) creates a subject on its first request and reuses it; fresh creates a new instance on every request. Each creation costs the subject's cost. With rights given, a protection proxy refuses any request whose client is not listed or whose subject is not among the client's; a refused request creates nothing and costs nothing, and its subject does not count as requested. Nothing is freed, so every instance created is alive at the end. The first request's cost is what the first request served pays (0 under eager, whose cost is paid at the start).

Method

Making a class keep its one instance

Four steps, the last of them on code of your own.

1

Ask whether one is a fact or a convenience

A single instance is a fact when two would be an error, as two spoolers would; it is a convenience when one simply suffices. Only the first needs the class to forbid a second.

2

Hide the constructor

Make the constructor private and give the class one static operation that returns the instance.

3

Choose when it is made

Create it on first use when it is costly or needs values known only later, and make the check safe if threads share it.

4

Do it on your own code

Find a shared object in a system you know: a configuration, a connection pool, a cache. Type its cost and a day's requests into the lab, count instances and cost under fresh and lazy, and note how a test would replace it.

Common mistakes

1
Treating a global variable as a singletonA global variable makes an object reachable, but nothing stops a second one being made, and every sole instance it holds adds a name to the global space. The pattern makes the class keep its own instance; on the lab's fresh preset five clients each making a registry pay 250 where one shared registry costs 50.
2
Creating every singleton at start-upThe static-object approach makes each singleton whether used or not, possibly before the values it needs are known, and in C++ in no defined order. Lazy creation in the access operation avoids all three; the lab's eager preset pays 20 for a log nobody asks for.
3
Choosing the subclass with conditionals in the access operationIt works, but the operation must be edited for every new subclass, which the authors say may matter for a framework's factories. Their registry of singletons removes the list, at the cost that every candidate must be created in order to register.
