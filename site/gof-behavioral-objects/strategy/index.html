Strategy

Strategy puts each algorithm of a family behind one interface, so the object that uses them can be configured with any. Read the pattern, then count the decision points of a print shop's code that tests the printing method in every operation, against the same prices as three printing strategies.

Strategy in five lines

Core ideas

What this lesson establishes

Three ideas from Strategy, the last of them what the lab counts.

1

Strategy and context

A strategy is an object that carries out one algorithm behind an interface every algorithm of the family shares. The context is the object that holds a strategy and calls it whenever it needs that algorithm done.

2

Taking the data to the strategy

One way to connect the two: the context passes everything the algorithm might need as arguments. The other is to pass the context itself, and let the strategy ask for what it needs.

3

Decision points

A count of the places code can go two ways: one, plus one for each if, while, for and case, and for each conditional and and or. Tests that ask which algorithm applies are the ones a Strategy moves.

The material

The pattern first, then the count

Read Strategy, in Chapter 5, Behavioral Patterns, in your own copy first. The lesson reads it section by section and then counts the tests one listing makes.

“Code containing many conditional statements often indicates the need to apply the Strategy pattern.” The sentence ends the third of Strategy's Consequences, in Chapter 5, Behavioral Patterns. The intent, in the lesson's words: make each algorithm of a family an object of its own, all behind one interface, so they can be swapped, and the code that uses an algorithm stays the same whichever is chosen. The book's other name for it is Policy.

The Motivation, summarised, is the case of breaking text into lines, for which there are many algorithms. Writing them all into the class that needs them makes it bigger, keeps algorithms you may not use, and makes a new one hard to add. So the book's text-composition class holds a compositor object, and three compositor subclasses implement a simple line-at-a-time method, a paragraph-wide optimizing one and one that fills each row with a fixed number of items. It is the same pair the case study met in Formatting, in Chapter 2. In short, the Applicability says: reach for it when there is more than one way to do a job, the ways can be swapped, and you would rather not see the choice written into conditionals or the ways' private data seen by their callers.

The participants are three: the Strategy, the common interface; each ConcreteStrategy, one algorithm; and the Context, which is configured with a concrete strategy, keeps a reference to it and may give it access to its own data. In the collaborations the context either passes the data the algorithm needs or passes itself so the strategy can call back. Clients usually create a concrete strategy and hand it to the context, and from then on deal with the context only.

Four of the Consequences are benefits. A hierarchy of strategies is a family that inheritance can factor. Strategy is an alternative to subclassing the context for each behaviour, which would fix the algorithm into the context and rule out changing it at run time. It removes the conditionals that pick a behaviour, as the opening quotation says. And it lets a client choose among implementations with different trade-offs of time and space.

Three are liabilities, and the authors put them plainly. Clients must know how the strategies differ to choose one, so the pattern belongs where the variation matters to clients. All strategies share one interface, so a context may prepare arguments a simple strategy never reads. And there are more objects, which stateless strategies shared among contexts can reduce, as Flyweight describes. The Implementation adds the choice between taking the data to the strategy, which keeps the two decoupled, and passing the context, which couples them more closely; strategies as C++ template parameters when the choice is fixed at compile time; and optional strategies, where a context with none falls back on default behaviour.

The Sample Code is the compositor example in C++, from InterViews, where the simple compositor ignores some of what it is passed and the fixed-row one ignores all of it. Known Uses ranges from ET++ and InterViews to a compiler's register allocators, a financial framework's pricing strategies, the Booch components' memory-allocation template arguments, a circuit-layout router and the validators of Borland's ObjectWindows, an example of the optional kind. Strategy's Related Patterns name only Flyweight, since stateless strategies make good flyweights. Two neighbours: Template Method varies part of an algorithm by inheritance, where Strategy varies the whole of it by delegation; and Domain-Driven Design's lesson Strategy and Composite in the Model reads the same pattern as a policy the business names.

long quoteCents(Job job) {
    int sheets = job.pages() * job.copies();
    switch (job.method()) {
        case OFFSET:
            if (job.copies() < 500) { return 9000 + 4 * sheets; }
            return 9000 + 3 * sheets;
        case RISO:
            return 2500 + 2 * sheets;
        case DIGITAL:
            return 20 * sheets;
        default:
            throw new IllegalStateException("no such method");
    }
}
int daysToPrint(Job job) {
    if (job.method() == Method.OFFSET) { return 5; }
    if (job.method() == Method.RISO && job.copies() > 1000) { return 3; }
    return 1;
}

Now the lab, on a print shop of the lesson's own, above. It quotes and schedules a job by the printing method on its ticket, and both operations test the method. On the preset print-by-method the lab counts 8 decision points: one to start, three cases, three ifs and one conditional and. The bands beside the count are McConnell's guidance from Code Complete, not this book's; the deepest nesting, 1, is first reached at line 4, inside the switch. Of the eight, five ask which method applies: the three cases and the first test of each if in daysToPrint.

interface PrintMethod {
    long quoteCents(int sheets, int copies);
    int daysToPrint(int copies);
}
class Offset implements PrintMethod {
    public long quoteCents(int sheets, int copies) {
        if (copies < 500) { return 9000 + 4 * sheets; }
        return 9000 + 3 * sheets;
    }
    public int daysToPrint(int copies) { return 5; }
}
class Riso implements PrintMethod {
    public long quoteCents(int sheets, int copies) { return 2500 + 2 * sheets; }
    public int daysToPrint(int copies) {
        if (copies > 1000) { return 3; }
        return 1;
    }
}
// Digital is written the same way, and tests nothing.

The preset print-methods is the same prices and times as printing strategies, above, and a job holds one, given at the counter: method.quoteCents(sheets, copies). The count falls to 3, one to start and two ifs, each a rule inside one method: offset's price break at 500 copies, risograph's slower run past 1,000. The five tests of which method applies are gone from the listing, though nesting is now 2, from line 7, since each test sits in a method in a class. The choice is made once, where the job is given its method, in code the lab is not shown. That is the first liability in a sentence: someone must know the strategies to choose one.

// A quiz app scores an answer by the round's mode.
int points(Answer a, Mode mode) {
    if (!a.correct()) {
        return 0;
    }
    if (mode == Mode.TIMED && a.seconds() < 5) {
        return 15;
    }
    if (mode == Mode.TIMED) {
        return 10;
    }
    if (mode == Mode.STREAK) {
        return 5 * a.streak();
    }
    return 10;
}

Then sketch classic, timed and streak scoring strategies, keeping the test of whether the answer is correct in the context, and count the context and the strategies together. How the lab reads Java
        
  • Comments run from // to the end of the line, or from /* to */; string and character literals are read as single tokens. The lab reads Java; it never runs it.
  • A line is blank, a comment line (it carries a comment, alone or after code) and/or a code line (it has code outside comments). A statement line is a code line that is not only braces and semicolons.
  • The routine is the first statement at brace depth 0 that ends in { and has the shape type name(parameters). Without one the listing is a fragment.
  • A variable is a name that begins with a lower-case letter or _, is not a keyword, is not followed by ( and does not follow a dot. Capitalised names are types or constants.
  • A declaration (a type, then a name and =, ;, , or :) sets the name when it has a value and only declares it otherwise; parameters are set on the header's line. name op expr with op one of = += -= *= /= %= reads the expression (and the name too, unless op is =) and then sets the name; x++ reads and then sets x. Setting an element or a field only reads the names in it. A for header is read as its three parts in order.
  • The lab reads the lines top to bottom and does not follow branches or loops.
Decision points: 1, plus one for each if, while, for, case, && and ||; else, default, do, ?:, try and catch add nothing. Depth is brace depth below the routine's own braces.

Moving an algorithm into strategies
Four steps, the last of them on code of your own.

      
1
Count the decisions
Count one, plus one for each if, while, for, case, && and ||. An else or a default adds nothing.
2
Mark the tests on the algorithm
For each decision, say whether it asks which algorithm applies or applies a rule within one. Tests of the first kind, repeated across operations, are what Strategy gathers.
3
Write one class per algorithm
Give each algorithm a class implementing every operation that varied, check each case gives what it gave before, and name the one place where a strategy is chosen.
4
Do it on code of your own
Find a method in code you know that switches on a mode, type or flag, count its decisions before and after strategies, and say whether its clients need to know which algorithm they get.

Common mistakes
1
Reaching for Strategy wherever an algorithm could varyThe book attaches a condition: clients must understand how strategies differ to pick one, so the pattern belongs where the variation is relevant to them. An algorithm that never varies in practice gains an interface, several classes and a choice someone must make, and nothing else.
2
Reading the falling count as the whole storyOn the lesson's illustration the decisions fall from 8 to 3 because the method is no longer tested in each operation. It is still chosen once, where a job is given its method, in code the lab does not see; and the strategies are more objects, which the book counts as a cost.
3
Shaping the interface around the first algorithmThe book stresses that the compositor's interface was designed to suit every layout algorithm, since changing it for each new strategy means changing every existing one. The Strategy and Context interfaces, it says, decide how well the pattern works.
