Layout and Style

Chapter 31 argues that the first job of layout is to show a program's logical structure, and that looking good comes a distant second. Find the lines of a short Java routine whose indentation tells a different story from the one Java reads, and say in words what the compiler does with them.

Core ideas

What this lesson establishes

The chapter rests on one principle and one fact about readers. The lesson adds the Java rule that makes the principle bite.

1

The Fundamental Theorem of Formatting

McConnell's name for the chapter's principle: good visual layout shows the logical structure of a program. Where showing the structure and looking good pull apart, showing the structure wins.

2

Two readers

The compiler reads braces, keywords and precedence, and ignores white space. A person reads the indentation first. A layout that agrees with the code tells both the same story; one that disagrees tells the person the wrong one.

3

The dangling else

In Java an if without braces governs exactly one statement, and an else belongs to the nearest if that does not yet have one, wherever the else is indented. A layout can put an else under one if while Java gives it to another.

The material

The chapter's argument, then a routine whose layout misleads

Read Sections 31.1 to 31.3 in your own copy first. The lesson sets out the argument section by section, then runs the chapter's test on three short routines.

Chapter 31, Key Points, p. 775. “The first priority of visual layout is to illuminate the logical organization of the code.” Chapter 31, Layout and Style, runs from page 729 to page 775. Read Sections 31.1 to 31.3 in your own copy before going on, and skim 31.4 to 31.8, which apply the same idea to control structures, statements, comments, routines and classes.

You have probably met this: an if with one statement and no braces, and later a second line added under it at the same indentation, because the indentation said that was where it belonged. It did not. Java gives an unbraced if exactly one statement, and the second line runs every time. Section 31.1 shows cases of this kind (pp. 732–733). Layout is the one part of a program that the compiler ignores and a reader cannot, so a listing can tell the reader one story and the compiler another. McConnell's name for the rule that follows is the Fundamental Theorem of Formatting: good visual layout shows the logical structure of a program. Making code look good is worth something, he says, but less than showing its structure, and where the two pull apart, the structure wins.

Why should the structure matter so much to a reader? The section answers with a line of research (pp. 733–734). Chase and Simon, the book reports, found in 1973 that chess experts remember the positions of pieces far better than novices when the pieces stand as they might in a game, and hardly better when they are placed at random; Ben Shneiderman, it reports, found the same of programmers in 1976, with program statements in a sensible order against the same statements shuffled. The book's reading is that experts carry a structure in their heads, and new material is easy to hold when it fits. So the details of a layout convention matter much less than following one consistently. McConnell tells a story to the point: Hank, a reviewer of his first edition, and Tony, a colleague of Hank's, had argued over brace placement for a whole project and ended it each preferring the style the other had started with.

Debates about layout, the chapter goes on, sound more like religious wars than discussions (p. 735), because layout is partly taste and partly logic. Its way through is to name the criteria. A good layout scheme represents the code's logical structure accurately, represents it consistently, makes the code easier to read, and survives modification, so that changing one line does not mean changing several others (pp. 735–736). Weigh the criteria differently and you may reach a different style; the point of naming them is that the reasons for a preference come out into the open.

Section 31.2 (p. 736) lists the tools, and white space is the main one: blank lines that divide a routine into paragraphs of related statements, and indentation that puts each statement under the one it is subordinate to. The book reports one study of indentation in some detail (p. 737). Miara and colleagues, in 1983, found that subjects scored 20 to 30 percent higher on a comprehension test with an indentation of two to four spaces than with none, and that six-space indentation scored second lowest, although many subjects felt it was the easier to use. That is one study's result, from its own subjects and programs, which the book offers as evidence that indentation is not cosmetic; it is not a measurement of your team. The section ends on parentheses: use more than you think you need, so that no reader has to work out the precedence.

Section 31.3 (p. 738) is about blocks, the statements under a control statement, and describes four styles. In a language with pure blocks, such as Visual Basic, every If has its End If and the layout follows naturally. In Java and C++ the braces are separate from the control statement, and that is where the trouble starts. You can emulate pure blocks, treating the opening brace as the end of the if line and the closing brace, aligned with the if, as the end of the construct, which the book calls standard in Java; you can treat the braces as the block's boundaries, indented with it; or you can use endline layout, which indents a block to wherever its control statement's line happens to end, and which McConnell rejects as inaccurate, hard to apply consistently and hard to maintain (p. 745).

Sections 31.4 to 31.8 (pp. 745–773) apply the principle to control structures, single statements, comments, routines and classes, and one passage matters most here (pp. 748–749). An if followed by a single statement needs no braces, and the book sets out the ways to lay it out. Leaving the braces out, it warns, invites someone to add a second statement under the if and forget to add them, a subtle error because the indentation says all is well while the compiler reads it otherwise. On a group project McConnell favours braces even round a single statement, and whichever style you choose, he asks that it be used consistently.

Now the code. The lab's layout view reads a Java listing, works out the depth that Java's structure gives each line, and compares the line's leading spaces with that depth times four, the indent this lesson uses. Its rules are under the listing: an unbraced if, else, for or while governs one statement, one level deeper, and an else belongs to the nearest if that does not yet have one. The Mis-indented lines tile counts the lines that disagree, the Which tile lists them, and each one is marked in the listing's gutter with a glyph and the word mis-indented. Here is the dangling-else preset, a routine that writes to a user by email or by letter:

void notifyUser(User user) {
    if (user.isActive())
        if (user.wantsEmail())
            sendEmail(user);
    else
        sendLetter(user);
    log(user);
}

Read it as the indentation invites. Line 2 tests whether the user is active; line 3, one level in, tests whether they want email; line 4 sends the email; and the else on line 5 sits at the depth of line 2, so it looks as if an inactive user gets the letter on line 6. Java reads it differently. Neither if has braces, so line 2's if governs the whole if statement that begins on line 3, and the else on line 5 belongs to the nearest if without one, the one on line 3. So an active user who wants email gets an email, an active user who does not gets a letter, an inactive user gets nothing, and line 7 logs every user. The lab agrees with Java: Mis-indented lines 2, Which 5, 6. The else belongs at the depth of line 3, eight spaces, and sendLetter at twelve. This is the dangling-else problem, and it is what the chapter means by a layout that tells the human one story and the computer another.

void close(Account account) {
    if (account.balance() == 0)
        account.markClosed();
        archive(account);
    log(account);
}

The two-statements preset is the case of page 749 in a routine of its own. Line 2's if has no braces, so it governs line 3 alone: an account with a zero balance is marked closed. Line 4, indented as if it belonged under the if, is simply the routine's next statement, and every account is archived, whatever its balance. The lab gives Mis-indented lines 1, Which 4. Nothing here is a syntax error, and nothing will tell you except a reader, a test, or a check of the layout against the structure.

void notifyUser(User user) {
    if (user.isActive()) {
        if (user.wantsEmail()) {
            sendEmail(user);
        } else {
            sendLetter(user);
        }
    }
    log(user);
}

The braced preset is the first routine with the braces the book favours on group projects, in the style it calls standard for Java. The structure is now in the code, where the compiler reads it, and the indentation shows you the same structure: the lab gives 0 and none. Whether the opening brace goes at the end of a line or on a line of its own is one of the questions the chapter treats as a matter of consistency rather than correctness, and this lesson leaves it there. A count of zero says only that indentation and structure agree. It says nothing about names, blank lines, or whether the routine does what it should.

Exercise

int clamp(int value, int low, int high) {
    if (value < low)
        return low;
    if (value > high)
        log("clamped");
        return high;
    return value;
}

clamp is meant to return value held between low and high, and to log when it clamps from above. Without the lab, mark every line whose indentation disagrees with the structure Java gives it, say in words which statement each if governs, and say what happens when you compile it. Then paste it into the lab to check the lines you marked; one of the quiz questions gives the answer.

How the lab reads Java
        
  • Comments run from // to the end of the line, or from /* to */; string and character literals are read as single tokens. The lab reads Java; it never runs it.
  • A line is blank, a comment line (it carries a comment, alone or after code) and/or a code line (it has code outside comments). A statement line is a code line that is not only braces and semicolons.
  • The routine is the first statement at brace depth 0 that ends in { and has the shape type name(parameters). Without one the listing is a fragment.
  • A variable is a name that begins with a lower-case letter or _, is not a keyword, is not followed by ( and does not follow a dot. Capitalised names are types or constants.
  • A declaration (a type, then a name and =, ;, , or :) sets the name when it has a value and only declares it otherwise; parameters are set on the header's line. name op expr with op one of = += -= *= /= %= reads the expression (and the name too, unless op is =) and then sets the name; x++ reads and then sets x. Setting an element or a field only reads the names in it. A for header is read as its three parts in order.
  • The lab reads the lines top to bottom and does not follow branches or loops.
Each line's expected depth: its braces, plus one for the single statement after an unbraced if, else, for or while; an else takes the depth of the if Java binds it to; a case label at the switch block's depth and its statements one deeper. Expected spaces are the depth times the lesson's indent; a tab counts as that many spaces.

Method
Checking a listing's layout against its structure
Five steps, the last on a routine of your own.

      
1
Find the control lines without braces
Mark every if, else, for and while whose line does not end in an opening brace. Each one governs exactly one statement: the next one.
2
Pair each else with its if
An else belongs to the nearest if above it that has no else yet and is not shut off by a closing brace. Write the pairs down by line number. An else sits at the same depth as its if, and governs one statement one level deeper, exactly as the if does.
3
Work out each line's depth
Count the braces open above the line, add one for each unbraced if, else, for or while whose one statement the line is, and multiply by the indent, four spaces here.
4
Compare, and say what runs
Mark each line whose leading spaces differ from its depth, and write one sentence on what Java does with it.
5
Check a routine of your own
Paste a routine of yours into the lab. If your team indents by two spaces, widen it first with a search-and-replace that turns each pair of leading spaces into four, and not with your editor's re-indent command, which would move every line to the depth Java reads and hide exactly what you are checking. If every indented line is flagged, the width is the cause. Note the Mis-indented lines count, and for each flagged line write one sentence on what Java does with it and whether that is what you meant.

Common mistakes
1
Thinking indentation is cosmeticThe thought is that the compiler ignores white space, so indentation cannot cause a defect. The first half is true, and it is the problem: the reader does not ignore it. In the dangling-else preset the layout says an inactive user gets a letter and Java sends nothing; in two-statements the layout says only closed accounts are archived and Java archives every one. Neither is a syntax error. The chapter's argument (pp. 732–733) is that a person reads structure from layout, so a layout that misstates the structure leads the next reader, and the next person to edit the routine, into the defect; the exercise is a defect the layout hid. The chapter grants that much of layout is taste, brace placement above all, and this lesson does not argue with that.
2
Choosing the layout that looks bestMany of the subjects in the study the book reports felt six-space indentation was easier to use, and it scored second lowest on comprehension (p. 737, after Miara and colleagues). Endline layout can look tidy on a short example and misstate the structure as soon as the conditions grow (pp. 743–745). The Fundamental Theorem puts showing the structure first and looking good a distant second.
3
Treating one brace style as the right oneMcConnell argues for some styles over others, by stated criteria, but his larger point is that the details of a convention matter less than following one consistently, and that a convention followed inconsistently can hurt readability (pp. 734, 775). Brace placement is the chapter's example of a religious issue, and its remedy is explicit criteria, not a winner.

Mark the mis-indented lines and say what Java does
Given a listing with unbraced ifs, such as the exercise's clamp, mark every line whose indentation disagrees with the structure Java gives it, and say in a sentence per line what the compiler does with it. You meet the standard when your marks match the lab's and each sentence names the statement the governing if controls.
Note: The evidence in this lesson is visual: a listing whose indentation disagrees with its structure. Read aloud, the indentation disappears, so the body states each routine's structure in words, and the listing marks a flagged line with a glyph and the word mis-indented, never by colour alone. The lab checks indentation against the structure Java gives each line, at four spaces a level, and nothing else. Code indented by two spaces must be widened to four first, by replacement and not by re-indenting; a tab counts as one level. The lab does not check blank lines, brace placement, line length or names, nor comment-only lines or the lines that continue a statement, and it cannot tell what the routine was meant to do. Most editors now re-indent code to its structure on request, which makes a dangling else visible to anyone who looks, and fixes nothing by itself.
