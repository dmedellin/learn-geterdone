Chapter 1 in six lines

Core ideas

What this lesson establishes

Chapter 1 uses three ideas that every later chapter assumes. The first is the distinction most often blurred.

1

Layer and tier

A layer is a logical division of the software; a tier usually means a physical one, a separate machine. Fowler uses layer to stress that the layers need not run on different machines: with a local database all three can run on one laptop and still be three layers.

2

The three principal layers

Presentation handles the interaction with the user or another program: it displays information and turns commands into actions. Data source talks to the systems that do work for the application, above all the database. Domain logic, also called business logic, is the work the application exists to do.

3

The dependency rule

The domain and data source never depend on the presentation: no call runs from them into presentation code. That makes it easy to put a different presentation on the same foundation and to change the presentation without consequences further down.

The material

The chapter's argument first, then the copied lines

Read Chapter 1, Layering, in your own copy first: its opening and its three sections. The lesson sets out its argument in its own words, then counts the lines a second presentation forces you to copy.

“The domain and data source should never be dependent on the presentation.” This is the one fixed rule in Chapter 1, Layering, in its section The Three Principal Layers, and the rest of the book keeps it. This lesson reads the whole chapter: what layers are for, how enterprise applications came to have three, what belongs in each, and where each should run. Read it in your own copy first.

Fowler's case for layers starts outside enterprise software, with network protocols: FTP on TCP on IP on ethernet. A higher layer uses the services of the one below and the lower is unaware of the higher. The benefits he lists follow: you can understand one layer without much knowledge of the others, replace a layer with another that offers the same services, minimise the dependencies between layers, standardise a layer, and build many higher services on one lower one. The costs are two. Layers do not encapsulate everything, so a new field that must be shown and stored ripples through every layer between; and extra layers can harm performance, though a layer that hides a function can also be optimised. The hardest part, he says, is deciding what the layers are and what each is responsible for.

The Evolution of Layers is a short history. Batch programs had none. The client–server tools of the 1990s, VB, Powerbuilder and Delphi among them, made two layers easy, with widgets that knew SQL, and worked well while the job was showing and updating rows. Domain logic was the trouble: written into the screens, it was awkward and easily duplicated, so a simple change meant hunting through many screens; written as stored procedures, it was poorly structured and tied to one vendor. The object community's answer was a third layer for the domain, and it made little headway until the Web, when every application whose logic lived in a rich client had to be rewritten to get a browser front end, while a well-layered one needed only a new presentation.

The Three Principal Layers names them, after Brown and his colleagues: presentation, domain and data source. Presentation is how the user, or a program, interacts with the software; data source is the communication with databases, messaging systems and other packages that do work for you; domain is the work itself, calculation, validation and choosing which data source logic to run. Fowler notes that the presentation often reads the data source directly, which is less tidy and, he concedes, often the better choice in practice. He contrasts his scheme with Alistair Cockburn's Hexagonal Architecture, which treats everything outside as one kind of interface, and keeps the asymmetry because a service you offer and a service you use are different. Separate the layers as the system needs, he advises, by subroutine, class or package, but separate them.

Then the test. People find it hard, he says, to tell domain logic from other logic, and his informal check is to imagine adding a radically different presentation, such as a command line to a Web application: whatever you would have to duplicate is domain logic that has leaked into the presentation. His example is a product list in which every product whose sales rose by more than 10 percent on the month before was coloured red, with the comparison done in the page. The domain should have a method that says whether sales are improving; the page asks it and chooses how to highlight. He will not be dogmatic about it: a reviewer, Alan Knight, wondered whether it was the start of a decline or a reasonable shortcut, and Fowler's answer is that it is both.

Choosing Where to Run Your Layers turns to machines. Running everything on servers is the simplest choice, because there is one place to upgrade and fix; the case for the client is responsiveness or working while disconnected. The data source runs on servers, the presentation wherever the kind of interface puts it, and Fowler, writing in 2002, favours a Web front end wherever it will serve and a rich client only where it must. Domain logic is best kept on the server; if a little must run on the client too, isolate it in a module that depends on nothing else. Keep the code in one process if you can, because separate processes cost performance and complexity. The chapter ends with the complexity boosters, Jens Coldewey's name for distribution, explicit multithreading, paradigm chasms such as objects and tables, multiplatform work and extreme performance requirements, for which the book's example is more than 100 transactions a second. Each has a cost, in building and in maintenance.

// Web page: show a product, red if sales rose more than 10%.
void showProduct(Product p, Page page) {
    long before = p.salesLastMonth();
    long now = p.salesThisMonth();
    boolean rising = now * 100 > before * 110;
    page.write(p.name(), now, rising);
}

// Command line: the same report, for a script.
void printProduct(Product p, PrintStream out) {
    long before = p.salesLastMonth();
    long now = p.salesThisMonth();
    boolean rising = now * 100 > before * 110;
    out.println(p.name() + " " + now + (rising ? " *" : ""));
}

Here is the book's red-product rule in code written for the lesson: a Web page and a command-line report, each deciding for itself whether sales rose by more than 10 percent. now * 100 > before * 110 is that test in whole numbers. The lab finds identical lines, two or more in a row, after collapsing white space. On the preset rising-twice it reports 1 repeated block, 6 lines in all the copies, and where: lines 3–5 and lines 11–13. Lines 6 and 14 differ, because each presentation shows the result in its own way. The 10 percent rule is the book's illustration; the code is the lesson's.

// Domain layer: the rule, in one place.
boolean isRising(Product p) {
    return p.salesThisMonth() * 100 > p.salesLastMonth() * 110;
}

// Presentation: the web page and the command line both ask.
void showProduct(Product p, Page page) {
    page.write(p.name(), p.salesThisMonth(), isRising(p));
}

void printProduct(Product p, PrintStream out) {
    String mark = isRising(p) ? " *" : "";
    out.println(p.name() + " " + p.salesThisMonth() + mark);
}

The preset rising-once is the same two presentations after the rule has moved into the domain as isRising. In a Domain Model it would be a method on Product; it is written here as a function so that both presentations fit in one listing. The lab reports 0 repeated blocks, 0 lines, and where: none. The two presentations still differ, one passes a flag to the page and the other appends a star, and that is the split Fowler describes: the domain decides whether there is something to highlight, and each presentation decides how. On the lesson's illustration the copied lines are three, and the count is a way of finding them, not a verdict on how bad they were.

One later view belongs here. Much presentation is now built in the browser, running as a program on the client and talking to the server through an API, and some applications run domain rules on both sides so that a form can answer at once. Those who build this way argue that the browser is now a capable client that updates itself, which removes much of the deployment cost that made Fowler favour the server. His chapter still frames the choice: a rule that runs in both places is the split he says sounds like the worst of both worlds, workable when it sits in a module that depends on nothing else, and an API is a second presentation, so his test applies to it.

How the lab reads Java
        
  • Comments run from // to the end of the line, or from /* to */; string and character literals are read as single tokens. The lab reads Java; it never runs it.
  • A line is blank, a comment line (it carries a comment, alone or after code) and/or a code line (it has code outside comments). A statement line is a code line that is not only braces and semicolons.
  • The routine is the first statement at brace depth 0 that ends in { and has the shape type name(parameters). Without one the listing is a fragment.
  • A variable is a name that begins with a lower-case letter or _, is not a keyword, is not followed by ( and does not follow a dot. Capitalised names are types or constants.
  • A declaration (a type, then a name and =, ;, , or :) sets the name when it has a value and only declares it otherwise; parameters are set on the header's line. name op expr with op one of = += -= *= /= %= reads the expression (and the name too, unless op is =) and then sets the name; x++ reads and then sets x. Setting an element or a field only reads the names in it. A for header is read as its three parts in order.
  • The lab reads the lines top to bottom and does not follow branches or loops.
This view compares statement lines as text, white space collapsed. A repeated block is a run of at least the lesson's minimum of consecutive statement lines that occurs again, not overlapping, and as long as it can be made at its start.

Method
Finding domain logic in a presentation
Four steps, the last of them on a screen you know.

      
1
Imagine the second presentation
Take a screen and imagine offering the same data another way: a command line, a report, an API. Write the second presentation, or sketch it.
2
Mark what you had to copy
Mark every line the second presentation repeats from the first. Those lines are domain logic that has leaked into the presentation.
3
Move the rule into the domain
Write one domain method that does what the copied lines did and returns the answer. Each presentation calls it and keeps only how the answer is shown.
4
Do it on a screen you know
Take one screen in a system you know. List each line of it that would be repeated if the same data were offered through an API, and count them.

Common mistakes
1
Thinking layers are tiers, so three layers need three machinesFowler separates the logical layers from where they run. Choosing Where to Run Your Layers is a separate decision, and its advice is to keep the code in one process where you can. The separation is worth having on one machine, because what it buys, understanding and replacing one layer without the others, has nothing to do with the hardware.
2
Thinking the rule is harmless in the page while there is one pageFowler's test is to imagine a second presentation, such as a command line: everything it would duplicate is domain logic. On the lesson's illustration that is three lines, copied into the second routine, and a change to the 10 percent would have to be made twice. Fowler does not call the first copy a disaster; with Alan Knight he finds it both sensible and the start of a slide, and the test tells you which side you are on.
3
Thinking the presentation must never touch the data sourceThe chapter's rule runs the other way: the domain and data source must not depend on the presentation. Fowler says the presentation more often reads the data source directly than not, which is less tidy and, he concedes, often the better choice in practice. A layered design forbids calls into the presentation, not every call that skips a layer.
