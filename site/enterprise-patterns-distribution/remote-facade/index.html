Remote Facade

Remote Facade puts a coarse-grained interface over a web of fine-grained objects, so that a remote client makes one call where it would have made several, while the objects behind it keep their small methods for local use. Compute the time fine-grained calls take across a network against the facade's coarse calls, and see how the saving depends on the latency.

Core ideas

What this lesson establishes

Three terms from the pattern. The second is the one Fowler insists on.

1

Remote Facade

A coarse-grained object at the process boundary over many fine-grained objects, which themselves offer only local interfaces; the facade translates each coarse call into the calls on them, and does nothing more.

2

No domain logic

Fowler's description of the facade: it holds no domain logic. Validation, computation and workflow stay in the fine-grained objects, or in a separate Transaction Script that is not remote, so that the whole application can run locally without the facade.

3

Bulk accessor

One getter or setter that reads or writes a group of values at once, such as a whole address, where the fine-grained object has one accessor for each value. A facade's methods are usually bulk accessors and commands, shaped for one client's screens.

The material

The pattern first, then the count

Read Chapter 15's Remote Facade in your own copy first, up to the end of When to Use It; the example that follows is worth reading in the book. The lesson sets out how the pattern works and then counts what one facade saves on two networks.

“Use Remote Facade whenever you need remote access to a fine-grained object model.” The previous lesson ended at the boundaries you cannot remove; this one reads the pattern Fowler puts on them, in Chapter 15, Distribution Patterns. It is a pattern, to be looked up and used, and the lesson reads it as a tool: what it is, what it must not hold, and when it pays.

The problem is the one Chapter 7 set. An object model works best with small objects and small methods, which gives control, substitution and names that reveal intent, and means many calls between objects. Between processes each call is expensive: data has to be marshalled, security may be checked, packets routed, and across the globe the speed of light starts to matter. Any object meant to be used remotely therefore needs a coarse-grained interface, and that affects the whole object structure: you update an order and its lines in one call, and give up the clear intent of small methods.

Remote Facade keeps both. It puts one coarse-grained object in front of a tangle of small ones, which stay purely local, and the facade contains no domain logic. All it does is translate. In the simplest case it replaces an address's getters and setters with one bulk getter and one bulk setter, which call the real object's accessors and do nothing more, so that validation and computation stay on the address. More often one facade has many methods, each passing on data from several objects, and Fowler prefers few facades with many methods each, a single facade even for a moderate application, where others make one per use case. A facade is designed for one client's usage, typically a family of screens, and two of its methods may do much the same thing underneath, because the client thinks of them as different commands.

Three further points from How It Works. A facade can be stateless, and pooled, or stateful, which makes Server Session State easy and may not scale to thousands of users. Its methods are the natural place for security and for transactions: start one, do the work, commit before the call returns. And it must stay thin. Fowler asks you to repeat a sentence three times, and it is worth repeating here once: “Remote Facade has no domain logic.” Workflow goes in the fine-grained objects or in a Transaction Script that is not remote, and the application should still run, whole, in one process with no facade at all. That is also how he tells it apart from the Session Facade of Alur, Crupi and Malks, which as usually described holds workflow logic, and from Stafford's Service Layer, in Fowler's book, which need not be remote and may sit under a facade.

When to Use It answers the quotation's question. Its usual place is where a user interface and a Domain Model run in different processes, such as a desktop client and a server model, or a servlet and an object model when the web and application servers are separate. Nor is a shared machine an exemption: two processes on one box, the section says, pay enough for each call to need a coarse-grained interface too. Within one process it is not needed, and it is not usually used with a Transaction Script, which is coarse-grained already. It implies synchronous calls, and Fowler notes that asynchronous messaging can do better, outside the book's scope.

// One remote call does the work of several local ones.
class CustomerFacade {
    private final CustomerRepository customers;

    CustomerFacade(CustomerRepository customers) {
        this.customers = customers;
    }

    void moveHouse(long id, String street, String city, String code) {
        Customer c = customers.find(id);
        c.address().setStreet(street);
        c.address().setCity(city);
        c.address().setPostcode(code);
        customers.save(c);
    }
}

The snippet is one facade method. A remote client calls moveHouse (lines 9 to 15) once, with the new street, city and postcode. Inside the server's process the facade makes five calls on the domain, besides fetching the address each time: it finds the customer, sets the three parts of the address one by one, and saves. Nothing in it decides anything. If a postcode must be checked against its city, that rule belongs to the address, where the local code that uses setPostcode gets it too.

Now the count. The lab reads records operation, fine: each record is one coarse-grained call that does the work of that many fine-grained ones. With the latency of a round trip and the work in each fine-grained call, it gives the round trips each way, the time of the fine-grained calls (each pays a latency and its work), the time of the coarse calls (one latency each, plus all the work), the share of the fine-grained time spent waiting, and the ratio of the two times. It assumes the work is the same either way.

The preset move-house has two facade methods, moveHouse, which does the work of 5 fine-grained calls, and showCustomer, a bulk getter in place of 6, at a latency of 20 ms and 0.5 ms of work a call. The fine-grained client makes 11 round trips and takes 451/2 = 225.50 ms, and 40/41 ≈ 97.6% of that is waiting; the facade makes 2, 91/2 = 45.50 ms, and the speed-up is 451/91 ≈ 5.0×.

The preset on-a-fast-network cuts the latency to 1 ms. Now the fine-grained calls take 33/2 = 16.50 ms, and 2/3 ≈ 66.7% of that is waiting, against 15/2 = 7.50 ms through the facade: 11/5 ≈ 2.2×. The facade removes waits, not work, so it saves most where the waits are most of the time. On the lesson's illustration the saving shrinks as the latency falls, but does not vanish. When to Use It goes further than any figure here: it says that even two processes on one machine pay enough a call to need the facade.

Method

Counting what a facade saves

Four steps, the last of them on a screen of your own.

1

Count the round trips

Add up the fine-grained calls each facade method replaces: that is the fine-grained client's round trips. The facade's are the number of its methods called.

2

Price the fine-grained calls

Each pays one latency and its own work: multiply the calls by the sum of the two.

3

Price the facade's calls

Each facade call pays one latency; the work of every fine-grained call is still done, inside the server. Add the two, and divide the first time by this one.

4

Do it on a screen you know

Take one screen in a system you know that calls a remote API. Count the calls it makes to draw itself, write the figure, and say in one sentence which of them one facade method could replace.

Common mistakes

1
Putting the business logic in the facadeThe facade is where the remote call arrives, so it looks like the place to decide things. Fowler calls this one of the biggest mistakes he sees: the facade is a thin layer that translates coarse calls into fine-grained ones, and the logic stays in the objects behind it. In the snippet, moveHouse sets the address and saves; any rule about addresses is the address's. Logic in the facade cannot be used by local code without going through it, and the whole application can no longer run without the facade.
2
Making the domain objects coarse-grained so they can be called remotelyIt removes the round trips, and gives up what the fine-grained model was for: small objects and methods that can be combined, overridden and read. The facade exists so that you do not have to choose. Local code keeps the fine-grained objects, and only the boundary gets the coarse interface, where it is obvious that a call is remote.
3
Thinking a facade matters only between machinesOn the lesson's illustration the facade saves least at the lowest latency, and it is tempting to drop it when the processes share a box. When to Use It says otherwise: a call from one process to another on the same machine still costs enough to want a coarse-grained interface, wherever the two processes run. The line Fowler draws is the process, not the machine.
