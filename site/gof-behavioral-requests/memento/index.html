Memento

Memento lets an object hand out a record of its own state that only it can read, so undo and checkpoints work without breaking its encapsulation. Read the narrow and wide interfaces, the cost of mementos and the case for storing only what changed, then run a map viewer's history and count the values kept as full snapshots against inverse operations.

Memento in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson, all of them the pattern's.

1

Originator

The object whose state is saved. It makes a memento holding a snapshot of its own internal state, and later restores itself from one; it alone decides what goes in.

2

Caretaker

The object that keeps mementos safe and passes them back, such as an undo mechanism. It never examines or changes what a memento contains.

3

Narrow and wide interface

The two faces of a memento. The caretaker sees the narrow one, which lets it hold the memento and pass it on and nothing more; the originator sees the wide one, which gives it everything it needs to restore itself.

The material

The pattern first, then its costs, then the count

Read Memento in your own copy first, including its Known Uses, which link it back to Iterator. The lesson reads the pattern as a tool and counts what a history keeps under two schemes.

“Without violating encapsulation, capture and externalize an object's internal state so that the object can be restored to this state later.” That is Memento's Intent, the last pattern of this course and the one that Command's undo and Iterator's cursors both point to. This lesson reads it section by section; read it in your own copy first.

The motivation is undo and checkpoints. To put an object back as it was, its state must be saved somewhere, yet an object normally hides its state, and exposing it would cost the reliability and extensibility encapsulation buys. The book's example is a graphical editor in which a constraint solver keeps connected shapes connected as they move. Undoing a move by moving the shape back the same distance need not put everything where it was, because the solver may have resolved slack differently, and the solver's public interface is not enough to reverse it exactly. So the editor asks the solver for a memento before the move and gives it back on undo, and the solver restores its own equations and variables from it.

The participants, as you would apply them. The Memento holds whatever part of the Originator's state the originator decides to put in it, and lets no one else at it. The Originator makes a memento of where it stands now and later resets itself from one. The Caretaker keeps the memento and never looks inside. The collaboration is short: the caretaker asks for a memento, holds it a while and hands it back, or never does if no undo comes. A memento does nothing by itself; only the originator that made it writes or reads what it holds.

final class TileView {                        // the Originator
    private int zoom, x, y;

    Snapshot save() { return new Snapshot(zoom, x, y); }

    void restore(Snapshot s) { zoom = s.zoom; x = s.x; y = s.y; }

    // The Memento. Its fields and constructor are private, so only the
    // enclosing TileView can make one or read it: the wide interface.
    static final class Snapshot {
        private final int zoom, x, y;
        private Snapshot(int zoom, int x, int y) {
            this.zoom = zoom; this.x = x; this.y = y;
        }
    }
}

Java gives the two interfaces directly, as the sketch shows: a nested class whose fields and constructor are private can be made and read by the class that encloses it and by nothing else, while any class may hold a reference to it. The book's C++ does the same by making the originator a friend of the memento, and its first implementation issue is exactly this: ideally the language offers two levels of protection. The pattern fits when two things hold together: an object must be put back to an earlier state, so part of that state has to be kept somewhere, and handing the state out through ordinary getters would show other objects how the object is built.

// The Caretaker keeps snapshots and hands them back. It sees only the
// type, which is the narrow interface: it cannot look inside one.
final class ViewHistory {
    private final Deque<TileView.Snapshot> saved = new ArrayDeque<>();

    void checkpoint(TileView view) { saved.push(view.save()); }

    void undo(TileView view) {
        if (!saved.isEmpty()) {
            view.restore(saved.pop());
        }
    }
}

Five consequences, and the authors are candid about the costs. Memento preserves encapsulation boundaries, keeping state only the originator should manage out of other objects' reach even though it is stored outside it. It simplifies the originator, which no longer keeps every version clients asked for. But mementos may be expensive, if the originator must copy a lot of state or mementos are made often; unless saving and restoring is cheap, the pattern may not fit. Some languages make narrow and wide interfaces hard to enforce. And there are hidden costs in caring for them: the caretaker cannot see how much state a memento holds, so a light caretaker can carry a heavy load.

The second implementation issue answers the cost. When mementos are made and returned in a predictable order, as on a command history where undo and redo go in sequence, a memento can store only the incremental change rather than the whole state, which is why a Command can keep just what it needs for undo. The Sample Code builds the editor's move command with a solver memento; the Known Uses are Unidraw's connectivity solver, the iteration state of Dylan's collections, a memento by another name, and the QOCA constraint toolkit, whose mementos hold only the variables that changed and so must be restored in order. Related Patterns: Command, which can keep undo state in mementos, and Iterator, since a memento can hold an iteration's state, as Dylan's collections do; Iterator's own Implementation calls its cursor a simple memento.

Now the lab, on a map tile viewer whose state is its zoom level and the position of its centre: zoom 3, x 120, y 80. Five commands: nearer and farther add 1 and −1 to the zoom, east adds 40 to x, home sets x to 0 and level sets y to 0. On the preset tiles the script zooms in twice, moves east, goes home, levels, undoes the level and zooms out. The final view is zoom 4, x 0, y 80; the undo stack holds 5 commands and the redo stack none, because farther discarded the 1 entry the undo had put there. Under the inverse scheme the history holds 1 value, the 160 that home replaced: each add is undone by subtracting, and the level that replaced a y value has gone with the discarded redo entry.

The preset tiles-snapshot runs the same script under the snapshot scheme, a full memento of all 3 cells for each of the 5 entries: 15 values against the inverse scheme's 1. The states are the same step for step; only what is kept differs. The preset scoreboard, a quiz app's six players, shows the cost growing with the originator: 5 entries, of which two are sets, hold 2 values as inverses and 5 × 6 = 30 as snapshots. That is the authors' warning about expensive mementos in a number. It is not a verdict on snapshots: an inverse is exact here only because adding whole numbers is exactly reversible, and the book's case for a memento is the solver whose effects are not.

Commands, undo and redothe undo and redo stacks after a sequence of commands

How the lab counts. A command name in the script runs it: set puts its amount in the cell, add adds it. Running a command pushes it on the undo stack and empties the redo stack, whose entries are discarded. Undo pops the undo stack, restores the state before that command and pushes it on the redo stack; redo pops the redo stack, runs the command again and pushes it back. An undo or redo with its stack empty does nothing and is counted. Stored values count what the history holds at the end, one entry per command on either stack: as inverse operations, one old value per set (an add is undone by subtracting its amount, which the command already holds); as snapshots, every cell of the state per entry. The states are the same under both.

Method

Counting what a history keeps

Four steps, the last of them on an application of your own.

1

Run the script

Work through the commands, undos and redos with two stacks, as in the lesson Command, and write the state after each step. The scheme does not change the states.

2

Count the snapshots

Under full snapshots, each entry on either stack keeps a memento of every cell: entries times cells, whether or not the command touched them.

3

Count the inverses

Under inverse operations, an addition is undone by subtracting and keeps nothing; a set keeps the one value it replaced. Count the sets on the two stacks.

4

Do it on an application of your own

Pick an object in a system you know that needs undo or a checkpoint. Estimate the size of its state and of a typical change, say whether every change can be reversed exactly from its inputs, and choose between snapshots and incremental mementos with a reason.

Common mistakes

1
Opening the originator's state so undo can save itGetters and setters for every private field let an undo mechanism save and restore an object, at the price the pattern exists to avoid: its implementation becomes everyone's business. A memento gives the saved state to the originator alone. On the lesson's illustration the ViewHistory stores 15 values it cannot read.
2
Assuming a memento is cheap because the caretaker isThe caretaker cannot see how much a memento holds, so a small history class can carry a great deal of state. The authors list this hidden cost, and the expense of copying large state often, among the consequences.
3
Undoing by inverse where the inverse is not exactMoving a shape back the distance it moved does not undo what a constraint solver did in between; that is the book's motivating case. An inverse operation is enough only when the change can be reversed exactly from its inputs; otherwise a memento of the state is needed.
