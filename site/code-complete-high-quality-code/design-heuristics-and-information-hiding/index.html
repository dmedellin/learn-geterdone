Core ideas

What this lesson establishes

Three terms run through section 5.3. The chapter treats each as a heuristic, a question worth asking, rather than a rule.

1

Abstraction

The ability to engage with a concept while safely ignoring its details. A class interface is an abstraction of the implementation behind it.

2

Encapsulation

The enforcer behind abstraction: not only may you ignore the details, you are prevented from looking at them. The chapter calls it the stronger of the two.

3

Information hiding

Each module is characterised by the design decisions it hides from all the others, its secrets. A secret might be an area likely to change, a file format or how a data type is implemented.

The material

The heuristics first, then one secret counted

Read sections 5.3 to 5.5, pages 87 to 123, in your own copy first; the heuristics take most of it. The lesson sets out the argument, then counts who knows one file format in two versions of a design.

“Information hiding is a particularly valuable concept. Asking ‘What should I hide?’ settles many difficult design issues.” That is one of Chapter 5's key points (p. 123), and this lesson reads the sections behind it: 5.3 on the heuristics, 5.4 on design practices and 5.5 on methodologies, pages 87 to 123. Read them in your own copy first.

If design is heuristic, as the first lesson read, the next question is which heuristics. Section 5.3 gives a list: find real-world objects; form consistent abstractions; encapsulate implementation details; inherit when that simplifies the design; hide secrets; identify areas likely to change; keep coupling loose; look for common design patterns. A shorter list follows, from strong cohesion and hierarchies to binding time, central points of control, brute force and drawing a diagram.

One heuristic gets several pages, and its history is a story with people in it. David Parnas introduced information hiding in a 1972 paper on the criteria for dividing a system into modules. Fred Brooks, in the first edition of The Mythical Man-Month, argued against it; in the twentieth-anniversary edition he took it back, and the book quotes him: “Parnas was right, and I was wrong about information hiding” (Brooks 1995). The book adds that Barry Boehm found it powerful for eliminating rework, especially where requirements change.

The idea is that each class, package or routine is characterised by the design decisions it hides from all the others. McConnell's example is an object id made by incrementing a global counter wherever an object is created. That spreads one decision, how ids are made, through every creation site; a single routine that hands out the next id keeps it in one place, and so can change it in one place. Secrets, the chapter says, fall into two kinds: hiding complexity, so you need not think about it, and hiding sources of change, so that a change stays local.

The section also lists what gets in the way: information spread through the system, such as one literal repeated everywhere; circular dependencies; avoiding class data from a fear of global data; and the worry that indirection costs speed, which it calls premature. Then come areas likely to change, with three steps: identify the items likely to change, separate each into its own class, and isolate it behind an interface that does not change with it. Business rules, hardware dependencies, input and output, status variables and data-size constraints are on its list of the usual suspects.

Section 5.4 turns from heuristics to practice: iterate; divide and conquer; work top down and bottom up, which it says are complementary rather than rival; build experimental prototypes; design with others, formally or informally; and capture the design cheaply, in comments, on a wiki, in photographs of a whiteboard. Section 5.5, on methodologies, comes back to how much design is enough: a judgement call, it says, but two amounts are wrong every time, designing every last detail and designing nothing at all, and dogmatic adherence to any one method hurts.

Now the count. The lab reads a design as records dependent, dependency and a module that changes, and prints two tiles: the modules that depend on it directly, and every module the change reaches by following the dependencies back, with each one's distance in the table. In exposed, five modules, invoice, report, export, audit and backup, each read a CSV file format themselves, and ui uses report. Change the format, csvformat, and the lab prints 5: audit, backup, export, invoice, report directly, and 6 reached, ui included.

In hidden the format is a secret of one module, store, and the five use store. Now the change reaches 1 module directly, store, and 7 in all: audit, backup, export, invoice, report, store and ui. The total went up by one, because store is new. What fell is the number of modules whose code knows the format, from 5 to 1, and that is the number the chapter cares about: those are the modules you would have to edit. The second tile counts something else, everything that depends on the format at any distance, which is what a build tool would recompile; Programming Tools, later in this path, uses it that way.

The lab cannot see whether store keeps its secret. If its interface hands back the raw line and lets each caller split it on commas, the records say one module depends on the format while five still know it. That is the question the chapter puts to every interface: what does this module hide, and does its interface give the secret away?

Method

Finding a secret and who knows it

Four steps, the last of them on your own code.

1

Name the decision

Say in a few words which design decision might change: a file format, a table's columns, how an id is made. That decision is the candidate secret.

2

List who knows it

List every module whose own code depends on the decision, the ones you would have to edit if it changed. That is the direct count.

3

Choose its keeper

Choose the one module that should know it, give it an interface that does not mention the decision, and redraw the dependencies so that the others use the keeper.

4

Do it on your own code

Pick one detail several modules of yours know, a file format, a table's columns or a URL scheme. Type the modules that know it as a, b records into the lab with the detail as the module that changes, note the direct count, and write the name of the module that should keep it.

Common mistakes

1
Thinking information hiding means fewer dependenciesIt sounds as if hiding should shrink the graph. On the lesson's illustration it does the opposite: in hidden the change reaches 7 modules, one more than the 6 in exposed, because the keeper store is new. What falls is the number of modules whose code knows the format, from 5 to 1. Section 5.3 measures information hiding by what a change makes you edit, and the two tiles count two different things.
2
Skipping the hiding for speedThe worry is that calling through an extra routine or class costs time. Section 5.3 names it as a barrier and calls it premature: until you can measure the program and find the slow spots, the best preparation for tuning is a modular design, in which a slow class can be rewritten without touching the rest.
3
Equating private fields with a hidden secretDeclaring the fields private hides the variables. It hides the decision only if the interface does too. A store that returns the raw CSV line and leaves callers to split it has private fields and a public secret: every caller still knows the format. The chapter's question is what the module hides, not which keywords it uses.
