Hashing with Chaining

Under simple uniform hashing the expected length of a chain is the load factor α = n/m, so a search costs Θ(1 + α) expected. That is an average over an assumption about the keys, and the worst case is Θ(n): no hash function removes it. At m = 8 and n = 20 the lab measures 2.3 probes on random keys and 10.5 on a key set with the same α.

Core ideas

What this lesson establishes

Three statements, and the third is the one that turns a slogan into an engineering fact. The first two are arithmetic; the third is what the arithmetic assumed.

1

The load factor is the answer, and it can exceed 1

α = n/m is the average chain length by definition: n keys shared over m slots. With chaining there is no upper limit on α — twenty keys in eight slots is α = 5/2 and the table works fine, just more slowly. A search costs one probe to find the slot plus a walk along the chain, which is Θ(1 + α), and the 1 matters precisely when α is small.

2

The expectation is over an assumption about the keys, not over the table

Simple uniform hashing says each key is equally likely to hash to each slot, independently of the others. That is an assumption about the input, and the hash function does not enforce it: h(k) = k mod m sends every multiple of m to slot 0 no matter how clever the rest of the table is. When the assumption fails the expectation says nothing.

3

The worst case is a linked list, and it cannot be engineered away

For any fixed hash function into m slots there is a set of n keys that all collide, because there are far more keys than slots. So the worst-case search is Θ(n), permanently. The honest statement is two-part — Θ(1 + α) expected, Θ(n) worst — and dropping the second half is how “hash tables are O(1)” gets said.

The material

The load factor, the expected chain, and the key set that defeats the table

Where the two expectations come from, the exact fractions at m = 8, and two key sets with the same load and very different costs.

Definition · Hashing with chaining

A table of m slots and a hash function h from keys to {0, …, m−1}. Each slot holds a linked list — a chain — of every key that hashed to it. Insert prepends to the chain; search computes h(k) and walks the chain; delete unlinks. The load factor is α = n/m, the number of keys divided by the number of slots.

The division hash function is h(k) = k mod m. It is the one this lesson uses, because its failure mode is arithmetic rather than mysterious.

Theorem · Expected search cost under simple uniform hashing

Assume each key is equally likely to hash to any of the m slots, independently. Then an unsuccessful search examines α keys in expectation, and a successful search examines 1 + α/2 − α/2m. Both are Θ(1 + α) once the constant probe for the slot itself is counted.

The unsuccessful case is immediate: the search walks the whole chain at h(k), whose expected length is n/m = α by linearity of expectation over the n keys. The successful case is smaller than α because the search stops at the key it wants and, on average, that key is halfway along — and the correction −α/2m is because the key being searched for is itself one of the n, so it does not collide with itself.

Linearity of expectation is doing all the work in the first half, and it is imported from Discrete Mathematics’ “Linearity of Expectation”: the expected number of keys in a given slot is the sum over keys of the probability that key lands there, which is n × 1/m. No independence is needed for that step, only for the assumption to be stated the way it usually is.

The fractions, at a table small enough to draw

Twenty keys into eight slots. The lab computes every quantity as an exact fraction over big integers, never as a decimal that is nearly one, and then counts the probes an actual search makes:

m = 8, n = 20 α = 20/8 = 5/2 = 2.5 expected unsuccessful α = 5/2 = 2.5 expected successful 1 + α/2 − α/2m = 1 + 5/4 − 5/32 = 67/32 = 2.09375 measured, twenty keys drawn from the stream: chains 4 5 1 2 0 1 4 3 longest 5, one empty mean probes over the twenty searches 23/10 = 2.3

23/10 against an expected 67/32: the measurement came in above the expectation, which is ordinary at twenty keys, and the two numbers are close. The chain lengths 4, 5, 1, 2, 0, 1, 4, 3 add to twenty and average 2.5, as they must — the average chain length is α by arithmetic, not by luck. What varies is how unevenly the keys landed, and the longest chain here is 5, twice the average.

The same load factor, and a table that has become a list

Now keep m = 8 and n = 20 and choose the keys to be 8, 16, 24, …, 160 — every one a multiple of 8. Each of them hashes to slot 0:

m = 8, n = 20, keys 8 16 24 … 160 α = 5/2, unchanged chains 20 0 0 0 0 0 0 0 longest 20, seven empty mean probes over the twenty searches 21/2 = 10.5 same α, expected 67/32 ≈ 2.09, measured 10.5 a factor of 5

The load factor did not move. The expectation did not move. The measured cost went up by a factor of five, and it is not a fluke or a bad seed — it is the worst case, reached deliberately, by keys that a real application produces all the time: record identifiers spaced by a round number, addresses aligned to a power of two, prices in whole units. The table is now a linked list with an index on the front of it.

So the quotable statement about a hash lookup has two halves and needs both: Θ(1 + α) expected under simple uniform hashing, Θ(n) in the worst case, for any fixed hash function. System Design’s “Hash vs Tree for Ranges” is where those same two facts decide a disk index rather than an in-memory one, and there the second half is joined by a third problem: a hash index cannot answer a range query at all, at any load factor.

Method

Costing a hash table

Compute the expectation first, measure second, and then try to break it — in that order, because the third step is meaningless without the first two.

1

Compute α, and keep it a fraction

n/m, exactly. 20/8 is 5/2, not 2.5 and certainly not 2. Every other quantity on the page is built from α, and a rounded load factor puts a rounding error into all of them.

2

Write both expectations down before looking at the table

α for an unsuccessful search, 1 + α/2 − α/2m for a successful one. They differ, they are both Θ(1 + α), and knowing which one a measurement should be compared with is half of reading the lab correctly.

3

Measure, and look at the longest chain as well as the mean

The mean is pinned to α by arithmetic and tells you nothing about spread. The longest chain is the cost of the unluckiest key, and at m = 8, n = 20 it is 5 — twice the mean, on keys that were drawn at random.

4

Now choose keys to defeat the hash function

For h(k) = k mod m, use multiples of m. The load factor will not move and the measured cost will. This step is the lesson: a structure whose guarantee is an expectation over the input has to be tested against the input that expectation assumes away.

Common mistakes

1
Saying a hash table is O(1) without the two qualificationsIt is Θ(1 + α) expected, under an assumption about the keys, and Θ(n) in the worst case. The short version is true of the cases most people meet and is not a bound. The habit worth building is to say the expectation and the worst case in the same breath, because a system whose input an adversary chooses will meet the second one.
2
Reading the load factor as a measurementα = n/m is arithmetic, and so is the mean chain length, which equals α on every key set whatsoever. Twenty keys in eight slots average 2.5 per chain whether they are spread evenly or all in one place. The quantity that distinguishes those two tables is the longest chain, and it is 5 in one and 20 in the other.
3
Testing a hash table only on keys that suit itRandom keys, sequential keys and keys drawn from a real trace all behave roughly like the expectation for h(k) = k mod m. Multiples of m do not, and they are not exotic: they arise from aligned addresses, round-numbered identifiers and strides in a loop. A table that has never been run on a degenerate set has not been tested, and the lab supplies one.

Check your understanding

✓
Finish when you can state the cost of a hash lookup in two halves without being prompted for the second.

You should be able to compute α and both expectations as exact fractions, say which expectation a given measurement should be compared with, produce a key set that sends every key to one slot for h(k) = k mod m, and quote Θ(1 + α) expected and Θ(n) worst case as a single two-part statement.

Note: Chaining pays for its collisions in pointers and never runs out of room. The alternative keeps everything inside the table and has a subtler problem: “Open Addressing and Linear Probing” shows why a deletion must leave a mark rather than a hole — the lab names the keys that go missing when it does not — and why clustering makes an unsuccessful search cost far more than 1 + α.
