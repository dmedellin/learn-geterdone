Composite

Composite builds a tree of objects in which a container and the things it contains share one interface. Read the pattern, including its trade-off between safety and transparency in declaring the child operations, then send one request down a garden's irrigation zones and count the calls, the total flow, and what happens when an emitter is asked to take a child.

Composite in seven lines

Core ideas

What this lesson establishes

Three terms carry the lesson: the roles, and the choice the authors spend longest on.

1

Component, Leaf and Composite

The Component declares the interface every object in the tree answers to. A Leaf has no children and does the work itself; a Composite stores children and usually carries out a request by forwarding it to each of them, perhaps doing something before or after.

2

Safety

Declaring the child operations, such as add and remove, only on the Composite class. Asking a leaf to add a child is then caught by the compiler, but leaves and composites no longer share one interface.

3

Transparency

Declaring the child operations on the Component, so that every object in the tree can be treated alike. A leaf asked to add a child then compiles, and must ignore the request or fail at run time. The book's pattern leans this way.

The material

The pattern, section by section, then the count

Read Composite in your own copy first. The lesson summarises its graphics example, reads the consequences and the nine implementation issues, and then counts the calls one request makes down a tree of its own.

“Composite lets clients treat individual objects and compositions of objects uniformly.” That is the second half of the pattern's intent; the first says what it builds, a tree of objects standing for a part–whole hierarchy. You met it in this path's case study, Design Problems and Document Structure, where the editor's page is built this way; here it is the catalog entry. Domain-Driven Design's lesson Strategy and Composite in the Model reads the same pattern as a concept in a domain; this lesson reads it as the authors wrote it.

The Motivation is a drawing program in which users group simple shapes into larger ones and group those again. With separate classes for the simple shapes and for the containers, every piece of code that handles them must tell the two apart, though the user hardly ever does. The pattern removes the distinction with one abstract class that stands for both: it declares the drawing operations and the operations for managing children, the simple shapes implement drawing directly, and the container class, a picture, draws by asking each child to draw. A picture can hold pictures, so the structure nests as deep as the user likes. Applicability is brief: use it for part–whole hierarchies, when code that uses the structure should handle one part and a group of parts alike.

Four consequences follow. Wherever the client expects a simple object it can be given a composite one. The client becomes simpler, with no type-testing code over the classes in the tree. New kinds of leaf or composite work with existing structures and clients unchanged. And the liability: the design can become too general, because the type system can no longer stop a composite from holding a kind of component it should not; that check moves to run time.

// The Component: every part of the system answers one question.
interface Watering {
    BigDecimal litresPerMinute();
}

final class Emitter implements Watering {             // a Leaf
    private final BigDecimal flow;
    Emitter(BigDecimal flow) { this.flow = flow; }
    public BigDecimal litresPerMinute() { return flow; }
}

final class Zone implements Watering {                // a Composite
    private final List<Watering> parts = new ArrayList<>();
    void add(Watering part) { parts.add(part); }   // declared here only: safe
    public BigDecimal litresPerMinute() {
        BigDecimal sum = BigDecimal.ZERO;
        for (Watering p : parts) { sum = sum.add(p.litresPerMinute()); }
        return sum;
    }
}

The Implementation section raises nine issues, and the fourth is the one the authors dwell on: where to declare the child operations. Declare add and remove on the Component and you gain transparency, since every node can be handled alike, at the cost of safety, since a client can ask a leaf for something meaningless. Declare them on the Composite alone, as the sketch above does, and the compiler catches the mistake, but leaves and composites now have different interfaces, and a client holding a component may need to find out whether it is a composite before adding to it. The authors say they have favoured transparency in the pattern, and suggest that a default add fail, by raising an exception, rather than quietly do nothing, since adding to a leaf probably means a bug.

// The transparent choice: add is declared on every component.
interface Watering {
    BigDecimal litresPerMinute();
    default void add(Watering part) {
        throw new UnsupportedOperationException("an emitter has no parts");
    }
}

The other issues, briefly. A child can keep an explicit reference to its parent, which makes moving up and deleting easier, provided the invariant is kept that a composite's children name it as their parent (changing the parent only in add and remove keeps it). Sharing components is hard when each has one parent; Flyweight is the way round it. The Component interface should be as large as can be made meaningful for both kinds, which pulls against the rule that a class should offer only what its subclasses can use. Keeping the child list in the Component costs space in every leaf. Children may need an order, and Iterator helps. A composite may cache results about its children, such as a bounding box, and must then be told when a change below invalidates the cache. Without garbage collection the composite should delete its children. And the structure holding the children is a matter of efficiency. Known Uses begin with Smalltalk's original view class, which was component and composite at once, and run through user interface toolkits, a compiler's parse trees and a financial portfolio of assets.

Now the lab, on a garden's irrigation system rather than the book's examples. Zones hold emitters and other zones; each emitter's value is its flow in litres per minute. Each record is node, parent, kind, value, with - as the root's parent and as a composite's value. On the preset garden-safe the lab counts 10 nodes: 6 leaves, 4 composites, and a depth of 3, down from the garden through the back zone and the beds to the herb drip. One request for the flow makes 10 calls: 1 from the client and 9 forwarded by composites, one call per node. The total is 29.75 litres per minute, and the table gives each zone's subtotal: front 6.5, back 17.25, beds 4.75.

The same preset asks two nodes to add a child: tap, an emitter, and beds, a zone. The zone does. The emitter's request is refused by the compiler, because under the safe declaration add exists only on Zone. On the preset garden-transparent the same request compiles, and the lab says the emitter must ignore it or fail at run time. Nothing else changes: the calls and the total are the same under either declaration, which is the point. The choice is about when a meaningless request is caught, not about what the tree computes.

A tree of partsone operation over a whole and its parts

How the lab counts. Each record is one node: its name, its parent (- for the root; exactly one root), its kind (a class name) and its value, a decimal for a leaf and - for a composite. A leaf has no children; a composite may have none. Children are taken in record order. A kind is either a leaf class or a composite class, never both. Depth counts the edges on the longest path down from the root (a root alone is at depth 0). One operation on the root makes one call per node: the client's call on the root, and one call from each composite to each of its children. The total is the sum of the leaf values, exactly; a composite's subtotal is the sum of the leaves below it, and its calls are the nodes in its subtree. A composite asked to add a child does. A leaf asked to: under the safe declaration (add declared only on the composite class) the call does not compile; under the transparent one (add declared on every component) it compiles, and the leaf ignores it or fails at run time.

Method

Reading a tree the way the pattern does

Four steps, the last of them on a structure of your own.

1

Sort the nodes

Mark each node a leaf, with a value, or a composite, with children. A kind of node is one or the other, never both.

2

Count the calls

One request to the root reaches every node once: the client's call and one call from each composite to each child. The calls equal the nodes.

3

Add up from the leaves

The total is the sum of the leaf values; each composite's subtotal is the sum of the leaves below it.

4

Do it on a structure of your own

Take a part–whole structure in your code (a menu, a bill of quantities, a folder tree) and write it as records. Count the calls and the total, and decide whether a leaf asked to add a child should fail at compile time or at run time in your design.

Common mistakes

1
Thinking the declaration of add changes what the tree computesSafety and transparency decide when a meaningless request to a leaf is caught, at compile time or at run time. On the lesson's illustration the calls and the total are the same under both, 10 calls and 29.75; only the outcome of asking the emitter differs.
2
Letting the client test which kind of node it holdsThe pattern exists to remove that code. If the client branches on leaf or composite for an ordinary request, the operation belongs in the Component interface, with each class answering it in its own way.
3
Caching a composite's result without telling it of changesThe authors allow a composite to cache what it learns about its children, and attach a condition: a change below must invalidate the caches above, which is easiest when children know their parents.
