Facade

Facade gives a subsystem one higher-level entry point, without hiding the classes behind it from clients that need them. Read the pattern, then count the uses between a parcel locker's three client applications and its subsystem, first going straight to the subsystem's classes and then through a facade.

Facade in six lines

Core ideas

What this lesson establishes

Three terms carry the lesson: the roles, and the two kinds of subsystem interface the authors distinguish.

1

Facade and subsystem classes

The Facade knows which subsystem classes handle a request and passes it to them, doing a little translation of its own where needed. The subsystem classes do the work and keep no reference to the facade.

2

Weak coupling

Few dependencies between a subsystem and its clients, so that the subsystem's classes can change without changing the clients. A facade reduces the uses that cross the subsystem's boundary to the facade itself.

3

Public and private subsystem interface

Like a class, a subsystem has a public interface, the classes any client may use, and a private one, for those who extend it. The facade belongs to the public interface but is seldom the whole of it.

The material

The pattern, section by section, then the count

Read Facade in your own copy first. The lesson summarises its compiler example, reads the consequences and the two implementation issues, and then counts the uses of a subsystem with and without a facade.

“Provide a unified interface to a set of interfaces in a subsystem.” That is the first sentence of Facade's intent; the second says the facade works a level above those interfaces, so the subsystem is simpler to work with. Its argument starts from the observation that dividing a system into subsystems reduces complexity, and that a common aim is then to have subsystems talk to and rely on each other as little as possible.

The Motivation is a programming environment's compiler subsystem: a scanner, a parser, the classes for the parse tree, a bytecode stream and a builder. A few specialised tools need those classes directly; most clients only want their code compiled. So the subsystem also offers a compiler class that does the common thing in one call and holds the rest together, without hiding the classes from the tools that want them. Applicability gives three cases: a simple default view of a subsystem that has grown complicated (patterns themselves tend to produce more and smaller classes, the authors note, which makes a subsystem more reusable and harder to use); many dependencies between clients and a subsystem's implementation classes; and layering, with a facade as each layer's entry point.

The participants are the Facade and the subsystem classes; the subsystem classes do the actual work and know nothing of the facade. Clients that use the facade need not touch the subsystem's objects at all. The Consequences are three benefits. The facade shields clients from the subsystem's components, so they deal with fewer objects. It promotes weak coupling: the subsystem's own classes are often tightly bound together, and a facade lets them change without the clients noticing, can remove complex or circular dependencies, and cuts the rebuilding that a minor edit to a central subsystem would otherwise trigger. And it does not stop applications from using the subsystem's classes when they need to, so each client can trade simplicity for the full set of options.

// The Facade: one entry point for what most clients want to do.
final class Lockers {
    private final LockerBank bank;
    private final DoorController doors;
    private final PinGenerator pins;
    private final SmsGateway sms;
    Lockers(LockerBank bank, DoorController doors,
            PinGenerator pins, SmsGateway sms) {
        this.bank = bank; this.doors = doors;
        this.pins = pins; this.sms = sms;
    }
    // A courier drops a parcel: find a locker, open it, text the PIN.
    Locker deposit(Parcel p) {
        Locker free = bank.freeLockerFor(p.size());
        doors.open(free);
        String pin = pins.issue(free, p);
        sms.send(p.phone(), "Locker " + free.number() + ", PIN " + pin);
        return free;
    }
}

Two implementation issues follow. Coupling can be reduced further by making the facade abstract, with a concrete facade for each implementation of the subsystem, or by configuring one facade with different subsystem objects. And a subsystem, like a class, has a public interface and a private one; making some subsystem classes private would help, but in 1995 few object-oriented languages could, and the authors note that the C++ committee had just added namespaces. The Sample Code builds the compiler facade in C++ and ends by weighing a parameter for the code generator, sensible if there is more than one target, against parameterizing every participant, which adds flexibility but works against the facade's purpose of simplifying the common case. Known Uses are the Smalltalk compiler that inspired the example, ET++'s browsing tools behind one class, and the Choices operating system, whose virtual memory framework has a facade. Related Patterns contrast it with Mediator, whose colleagues talk to it, where subsystem classes do not know a facade exists, and note that a facade is often a Singleton.

Now the lab, on a parcel locker rather than the book's compiler. The subsystem has five classes: LockerBank, DoorController, PinGenerator, SmsGateway and Ledger. Three applications use it: a courier's app, the kiosk at the lockers and the support desk. Each record is one use, user then used. On the preset direct every client reaches into the subsystem for what it needs: the lab counts 8 classes and 12 distinct uses, so 12 of the 28 possible pairs are connected, 3/7 or about 42.9%. The courier app has the largest fan-out, 4, and LockerBank the largest fan-in, 4. Ten of the twelve uses cross from a client into the subsystem; the other two are the subsystem's own.

On the preset through-facade a Lockers class stands in front. The courier app and the kiosk use only Lockers; the support desk uses it too, and still reads Ledger directly, because the pattern does not forbid that. The lab counts 9 classes, one more, and 10 uses, 10 of 36 pairs (5/18) or about 27.8%. The largest fan-out is now the facade's, 4, and so is the largest fan-in, 3: every client uses it. Count the uses that cross the boundary yourself from the records: four, three to the facade and the desk's one to the ledger, where there were ten. The subsystem's classes can now change behind Lockers, and only the desk's one direct use goes with them.

The lab's figures are of the design as written. The facade concentrates the fan-out in one class, which is the point and also a thing to watch: a facade that takes on every client's special case grows into the subsystem's whole interface again, which is the trade-off the Sample Code ends on.

Exercise

The support desk is changed to read the ledger through Lockers as well, so the facade uses all five subsystem classes. By hand, give the classes, the distinct uses, the uses that cross from a client into the subsystem, and the facade's fan-out. Edit the preset's records in the lab to check.

Method

Measuring what a facade changes

Four steps, the last of them on a subsystem of your own.

1

Draw the boundary

List the subsystem's classes and the clients outside it. A facade belongs inside the boundary, with the classes it fronts.

2

Count the uses that cross it

Count every use from a client to a class inside, before and after the facade. Leave the subsystem's own uses out: a facade does not change them.

3

Keep the direct uses that are needed

Mark the clients that need something the facade does not offer. They may keep using the subsystem's classes; the pattern allows it.

4

Do it on a subsystem of your own

Take a package your code reaches into from several places and write its uses as records. Count the uses that cross its boundary, then sketch the facade's few operations and count again.

Common mistakes

1
Thinking a facade hides the subsystemThe authors say plainly that it does not prevent clients from using the subsystem's classes. It offers a simpler default for most clients, and those who need more look past it. On the lesson's illustration the support desk keeps its one direct use, and the count shows it.
2
Expecting a facade to remove the subsystem's own couplingA facade changes the uses that cross the boundary, not the ones inside. The subsystem's classes may still be strongly bound together; the facade lets them change without the clients noticing.
3
Giving the facade every option the subsystem hasA parameter or two can earn its place, as the code generator does in the authors' Sample Code; parameterizing every participant, they note, detracts from the facade's purpose, which is to make the common case simple. A client that needs the options can use the subsystem's classes directly.
